This is not a wording preference; it changes three things concretely:

1. **Change 2's probe is a capability detector, not a fault detector.** It reads the current behaviour at runtime instead of encoding a belief about it, so a change in either direction is picked up without a code edit.

## Part 2 — NoteEntity vs nested search: do the counts agree?

**Yes, exactly.** Both methods were run to completion for `action = "Agent added"` and cross-checked as sets, not just as totals:

| Method | Result |
|---|---|
| `/query/NoteEntity` `where=note.action='Agent added'`, fully paginated | **92 note rows**, **71 distinct `targetEntityID`**, `targetEntityName` = `'User'` on all 92 |
| `/search/Candidate?query=notes.action:"Agent added"` | **71** |
| `/search/ClientContact?query=notes.action:"Agent added"` | 0 |
| `/search/JobOrder?query=notes.action:"Agent added"` | 0 |
| Set difference, NoteEntity IDs vs nested Candidate IDs | **0 in either direction. Identical sets.** |

Two independent methods, one going through an unindexed join table and one through the Lucene index, agreeing on the same 71 record IDs with no discrepancy. That is the strongest validation available without a database dump, and it is why Change 1 can be built on the nested pattern with confidence.

**The one difference is semantic, and it matters when you report a number:**

- **92** is the number of *notes*. A candidate with three `Agent added` notes contributes three rows.
- **71** is the number of *candidates*. Nested search returns parent records, deduplicated by nature.

Neither is wrong; they answer different questions. "How many notes were logged" is 92. "How many candidates were touched" is 71. The `note_action` parameter in Change 1 answers the second, which is what was asked for, and its docstring must say so explicitly so nobody reports 71 as a note count.

The ClientContact and JobOrder zeros are genuine absence of data, not failures: `Agent added` notes come from the candidate application triage flow, so they only exist on candidates. `notes.action:"BD Call"` on ClientContact returns 1978, confirming the mechanism works there too.

**Practical consequence:** the nested path answers the record-level question in one call with a real `total`, so it wins for anything the list tools do. NoteEntity is only needed for note-level counts and for retrieving note rows themselves. It stays deferred.

## Part 3 — `/query/NoteEntity` (evidence on file; DEFERRED, superseded by Change 1)

**Read Change 1 first.** The nested `notes.action` pattern beats everything below for the actual use case, needs no code, and rides a healthy index. This part is retained because it is verified evidence and because NoteEntity remains the only way to retrieve *note rows themselves* tenant-wide, should that ever be needed. It is not the recommended path.

**Answer to the direct question:** `get_notes_for_entity` per record is **not** the only option. `/query/NoteEntity` filters notes tenant-wide by any Note field in a single call. Verified:

```
GET .../query/NoteEntity
    ?where=note.action='Agent added'
    &fields=id,note(id,action,dateAdded,comments),targetEntityID,targetEntityName
    &count=5&orderBy=-note.dateAdded
HTTP 200
{"start":0,"count":5,"data":[
  {"id":14722698,"note":{"id":2650796,"action":"Agent added","dateAdded":1785141332693,
    "comments":"Auto-added by Application Triage (Stage 2). Action: CREATE. Source: Irish Jobs. ..."},
   "targetEntityID":172229,"targetEntityName":"User"},
  ...]}
```

Verified capabilities and limits:

| Capability | Status | Detail |
|---|---|---|
| Filter on `note.action` | works | as above |
| Filter on `note.isDeleted` | works | `note.action='Agent added' AND note.isDeleted=false` → HTTP 200 |
| Filter on `note.dateAdded` | works, **format-sensitive** | **Bare unquoted epoch ms is the documented format and works**: `note.dateAdded>=1784592000000`. The quoted string `'2026-07-21 00:00:00.000'` also works and returns identical row counts. Rejected with 400: `'2026-07-21'` ("too short"), `'20260721000000'` ("malformed"), `'2026-07-21T00:00:00'` ("too short"), and **quoted** epoch ms `'1784592000000'` ("malformed"). The quotes are what break epoch ms, not the format |
| **Epoch seconds trap** | **silent wrong answer** | `note.dateAdded>=1784592000` (seconds, not ms) returns HTTP 200 and **92 rows — identical to no filter at all**, because as ms it evaluates to 1970. A units mistake here does not error; it silently widens the filter to everything. Must be guarded |
| Sort via `orderBy=-note.dateAdded` | works | |
| Retrieve `note.comments` | works | full comment body, so text filtering is possible client-side |
| `total` in the response | **absent** | `/query` responses carry only `start`/`count`/`data`. Pagination must loop until a short page. This breaks the `_paginate_envelope` contract, which needs `total` |
| `targetEntityName` | **unreliable** | Returns `"User"` for Candidate notes, exactly the CR23 quirk. Cannot be used to filter by entity type |
| `/search/NoteEntity` | **does not exist** | 400 `errors.searchUnknownEntity` |
| `/meta/NoteEntity` | works | exposes only 4 fields: `id`, `note` (TO_ONE), `targetEntityID`, `targetEntityName` |

Because `targetEntityName` is garbage, resolving "which of these are Candidates" requires intersecting `targetEntityID` against a candidate ID set. End-to-end verification of the original question — candidates added since 21 Jul 2026 that also carry an `Agent added` note — in 2 query families instead of 97 per-candidate calls:

```
/search/Candidate?query=dateAdded:[20260721000000 TO 20260729000000] AND isDeleted:0
  → total=97
/query/NoteEntity?where=note.action='Agent added'
                   AND note.dateAdded>='2026-07-21 00:00:00.000'
                   AND note.isDeleted=false
  → 89 rows, 68 distinct targetEntityIDs
intersection → 38 candidates
```

38 of the 97 candidates added in that window have an Application Triage note. That is the answer the original request wanted.

## Part 4 — Proposed changes

### Change 1 (primary): make note-field filtering discoverable

#### The actual defect, stated precisely

The request was: *find contacts where a note action matches a given value.* That is a supported, working query on this tenant:

```
GET /search/ClientContact?query=notes.action:"BD Call"        → total: 1978
```

The server could have answered it on day one. It did not, because **nothing in the tool surface tells the agent that note fields are reachable as nested fields on the parent entity.** Every tool description points at either `/search/Note` (dead on this tenant) or `get_notes_for_entity` (one record at a time). The working pattern is invisible.

That is the defect. Not the Bullhorn index, not our request construction, not our response parsing. A capability that shipped and works was undiscoverable from the interface that is supposed to describe it.

Five things made it undiscoverable, and each needs its own fix:

| # | Cause | Fix |
|---|---|---|
| 1 | No tool description mentions nested association fields at all | Deliverable A |
| 2 | The `Note` field reference in tool descriptions renders **empty**, so `action` and its 25 picklist values were never shown to the agent | Part 5 / Change 3. This is now a primary fix, not a side issue |
| 3 | `search_notes` actively misdirects: it names a UI setting and tells the reader to contact support | Part 6 item B, plus Deliverable A |
| 4 | Every wrong guess returned HTTP 200 with `total: 0`. No error, nothing to learn from, so the agent concluded "no such notes exist" | Change 2 warning, plus Deliverable C |
| 5 | Two of the four plausible entry points cannot work by design (`query_entities("Note")` is hard-refused; `/query/Candidate` 400s as an indexed entity), so early attempts were spent on dead ends | Deliverable A cross-references |

#### Verified dot-path inventory

This list is **empirically established, not derived**. See the "why not auto-generate" note below.

Verified working on Candidate, ClientContact and JobOrder:

| Path | Candidate | ClientContact | JobOrder |
|---|---|---|---|
| `notes.action:"BD Call"` | 221 | 1978 | 34 |
| `notes.comments:"Application Triage"` | 71 | 0 | 0 |
| `notes.dateAdded:[20260721000000 TO 20260729000000]` | 173 | 40 | 2 |
| `notes.commentingPerson.id:142235` | 20 | 15 | 0 |

Zeros above are genuine absence of data, not failures: "Application Triage" notes exist only on candidates. Confirmed by `notes.id:[0 TO 999999999]` returning 67,784 / 47,512 / 18,220 against baselines of 104,556 / 63,746 / 50,271, i.e. the association filters correctly on all three.

**`notes.isDeleted` does NOT work.** `notes.isDeleted:0` returns 0 on all three entities. Do not document it and do not add it to any generated query. The parent's own top-level `isDeleted:0` works normally and the existing auto-append is unaffected.

Other association paths that filter correctly (recorded for future use, not part of this CR): `educations.*` and `fileAttachments.*` and `placements.*` on Candidate, `jobOrders.*` on ClientContact, `submissions.*` on JobOrder.

#### Why this must NOT be auto-generated from /meta

Tempting, since `/meta/Candidate` lists `notes` as `TO_MANY` with `optionsType: Note` and `hideFromSearch: false`, and we already fetch `/meta/Note`. Rejected, because **`hideFromSearch` does not predict searchability.** No Candidate association has `hideFromSearch: true`, yet several dot paths return 0 while others filter correctly. Auto-generating would emit confident, wrong guidance for paths that silently return nothing, which is worse than saying nothing: it would teach the agent to trust a query that lies.

Curated allowlist only. Add a path after testing it, never on the strength of `/meta` shape.

#### Three silent-failure modes that must be documented

Lucene fails quietly in both directions here, which is precisely why five attempts produced no diagnosis:

| Mistake | Result | Why it is dangerous |
|---|---|---|
| Multi-word value unquoted: `notes.action:Agent added` | `total: 0` | Looks like "no matches". `notes.action:"Agent added"` gives 71. Quoting is mandatory for every multi-word picklist value |
| Malformed clause, e.g. a missing colon: `notes.id[0 TO 999]` | **matches every record** | Returns the full entity count with HTTP 200. Reads as a successful broad query. I hit this myself while building the table above |
| Non-existent path: `notes.notARealSubfield:"x"` | `total: 0` | Indistinguishable from a real empty result |

Case-insensitivity and wildcards do work: `notes.action:"agent added"` and `notes.action:Agent*` both return 71.

#### Deliverables

**A. Teach the pattern in the tool descriptions.** The primary fix. Add to `search_entities`, `list_contacts`, `list_candidates`, `list_jobs`, and `search_notes`:
- The verified paths from the inventory above.
- A worked example that combines a note filter with a parent filter, because that combination is the whole point and is not guessable: `notes.action:"BD Call" AND status:Active`.
- The explicit statement that results are **parent records, not notes**.
- The quoting rule, prominently.
- That `notes.isDeleted` is unsupported.
- In `search_notes`: that the Note index returns nothing on this tenant, and where to go instead. Replaces the misdirection removed in Part 6 item B.

**B. A `note_action` parameter on `list_contacts`, `list_candidates` and `list_jobs`. APPROVED 2026-07-28.** The reason is the defect itself. A docstring paragraph only helps an agent that reads prose and then correctly composes Lucene, including the quoting rule it just learned. A typed parameter is self-describing in the tool schema, cannot be mis-quoted because we build the clause, and is discoverable by an agent scanning parameter names. Given the complaint is "the tool could not discover the method", making the method a named parameter is the most direct possible fix.

Implementation: validate against the live `Note.action` picklist via the existing `_load_valid_note_actions(metadata)`, reject unknown values with the valid list in the error, and build `notes.action:"<value>"` with the quoting handled. Reject values containing `"` or `'`. Adds no tools; three parameters on three existing tools.

**C. No new tool, and the NoteEntity backend stays deferred.** Tool count remains 38.

**D. Source the valid note actions during the startup inventory build.** Raised by the owner, 2026-07-28. Two distinct things sit behind this, and the answer differs for each.

*The validation cache is already correctly plumbed; do not add a startup fetch.* `_load_valid_note_actions(metadata)` (server.py ~line 2771) calls `metadata.get_fields("Note")`, and `BullhornMetadata` caches per entity. `main()` already assigns enrichment's own metadata instance to the global: `_metadata = asyncio.run(enrich_tool_descriptions(mcp, get_client()))`. Since enrichment fetches `/meta/Note` for all `SUPPORTED_ENTITIES`, the Note picklist is **already warm** by the time any tool runs. Validation therefore costs zero extra API calls. Eagerly materialising `_valid_note_actions` at startup would add a failure path for no gain and would break the "enrichment is additive and optional" invariant. Leave it lazy; add a comment recording why, so this question is not re-asked.

*Inlining the values into the tool description IS worth doing, and is the real substance of the request.* That is what `PICKLIST_FIELDS_TO_EXPAND` does, and `action` is missing from it (Part 5 Bug B). Adding it means the agent **sees the 25 valid actions in the tool description at startup** without calling anything. Combined with the `note_action` parameter, the agent gets both the parameter and its legal values up front, which is the complete discoverability fix. This single line is the highest-value change in the CR for agent UX.

*Required fallback behaviour.* If the picklist is unavailable (`_load_valid_note_actions` returns `None` when `/meta` fails), `note_action` must **not** block the query. Build the clause and proceed. Blocking a working search because a metadata call failed would convert a degraded-but-usable server into an unusable one, and it contradicts the additive-and-optional invariant. Add a test for the `None` path.

#### The one real risk

The dot-notation syntax is **undocumented**. Bullhorn's `_search.md` covers `fields`, `query`, `sort` and `count`, and links out to generic Lucene docs; it says nothing about nested or associated-field search. This is verified-working, not contractually guaranteed.

Mitigation is a live canary in `smoke_read.py`. Per the standing assumption it watches for **change in either direction**, not for breakage, and asserts two things:

1. `search('ClientContact', 'notes.action:"BD Call"')` returns a non-zero total (1978 at time of writing; assert `> 0`, never the exact number).
2. `search('Note', 'id:[0 TO 99999999]')` — record the total. Zero today. **If this ever becomes non-zero, `/search/Note` has started returning results** and the Change 2 warning will stop firing on its own. That is not a failure; it is the signal to reconsider which route we prefer.

A mocked test cannot catch either shift, by definition. If assertion 1 ever fails, the NoteEntity design in Part 3 is the fully-evidenced fallback. Neither outcome implies anything is wrong on Bullhorn's side.

### Change 2: `search_notes` must not return a silent empty envelope from a route that returns nothing here

**The problem.** Today, `search_notes("Auto-added by Application Triage")` and `search_notes("asdfghjkl")` return byte-identical responses: `{"data": [], "pagination": {"total": 0, ...}}`. One of those phrases is in thousands of notes and the other is in none. The tool cannot tell the difference, so neither can the agent, and neither could you — which is exactly how this investigation started. The agent's only reasonable reading of an empty result is "there are no such notes", so it reports that confidently and stops. An unusable route is being rendered as a factual answer about your data.

**The fix.** Distinguish "no matches" from "the index cannot answer questions at all", using the probe this investigation validated. On a `total: 0` result from the Lucene branch, issue one match-all query:

```python
search('Note', 'id:[0 TO 99999999]', fields='id', count=1)
```

If that *also* returns `total: 0`, this route returns nothing on this account, so the empty result says nothing about the caller's query. Return the normal envelope plus a `warnings` key stating that plainly and naming the routes that do work: `entity_filter`, `get_notes_for_entity`, the new `note_action` parameter, and the nested `notes.action` pattern for hand-written queries. If the probe returns a non-zero total, the route is usable and the empty result is a genuine "no matches" — emit no warning.

**Wording constraint on the warning.** It must describe observed behaviour, not diagnose Bullhorn. Say what this route returns on this account and where to go instead. Do not use "broken", "misconfigured", "outage", or "not enabled", and do not tell the reader to contact Bullhorn. We do not know their intent, and the working route may well be the intended one.

Cache the probe verdict per process, same shape as `_isdeleted_cache`, so it costs one extra call per server lifetime rather than one per search.

Two reasons this matters. First, it converts a silent wrong answer into a loud correct one, which is the single highest-value reliability change in this CR. Second, and more importantly under the standing assumption below, **the probe is a capability detector, not a fault detector.** It reads the current behaviour at runtime rather than hard-coding a belief about it. If `/search/Note` ever starts returning results, the warning disappears by itself with no code change and no stale docstring. That is the "we will adjust when it changes" principle implemented in code rather than left to someone noticing.

**Do not use `fieldsFromIndex` for this.** That is the false signal documented in Part 1 finding 4 and Part 6; working searches return `false` too. The match-all probe is the reliable test.

This is additive: `data` and `pagination` keep their current shape.

## Part 5 — Separate bug: empty Note and CorporateUser field metadata at startup

**This is our bug, and it is independent of the search problem.** Both `/meta` calls succeed:

```
GET .../meta/Note?fields=*&meta=full        → HTTP 200, 20,904 bytes, 27 fields
GET .../meta/CorporateUser?fields=*&meta=full → HTTP 200, 46,992 bytes, 91 fields
```

Bullhorn returns the data. `select_fields()` in `src/bullhorn_mcp/descriptions.py` throws it away. Observed by running the real enrichment path against the live tenant:

```
Note:          /meta returned 27 fields;  select_fields kept 0
CorporateUser: /meta returned 91 fields;  select_fields kept 30
Candidate:     /meta returned 277 fields; select_fields kept 40
any required flag set?  False   (for all three entities)
```

Three distinct defects compound here.

### Bug A: `get_meta()` omits `meta=full`, so `required` is never populated — for any entity

`client.get_meta()` (src/bullhorn_mcp/client.py:587) sends `params = {"fields": "*"}` only. Bullhorn omits the `required` key entirely unless `meta=full` is passed. Proven:

```
/meta/Note?fields=*            → action keys: [confidential, dataType, hideFromSearch,
                                  label, maxLength, name, options, type]
                                 required present? False
                                 fields with required=True: 0/27
/meta/Note?fields=*&meta=full  → action keys: [..., optional, options, readOnly, required, ...]
                                 required present? True  value=True
                                 fields with required=True: 1/27
```

Consequence: `metadata.get_fields()` hard-codes `"required": bool(f.get("required", False))` → always `False`. So **step 2 of `select_fields()` (required fields) has never selected a single field for any entity**, and the `[required]` marker in `build_entity_section()` has never once rendered. This is a silent 10-sprint-old latent bug that CR18 introduced and no test caught.

Fix: `params = {"fields": "*", "meta": "full"}`. Cheap, but it changes the payload for every `/meta` consumer, so re-run the token-cost measurement afterwards (`bullhorn-mcp-run-and-operate`) — richer field dicts mean nothing extra in the rendered output today, but `[required]` markers will start appearing and that is a real token delta.

### Bug B: `Note` and `CorporateUser` are the only `SUPPORTED_ENTITIES` absent from `DEFAULT_FIELDS`

```python
>>> [e for e in SUPPORTED_ENTITIES if e not in DEFAULT_FIELDS]
['Note', 'CorporateUser']
```

`select_fields()` step 1 seeds from `DEFAULT_FIELDS`; with no entry it contributes nothing. Combined with Bug A killing step 2, Note falls through to step 3 (`status`/`employmentType`/`category`/`type`/`source` — Note has none of those field names; its picklist is `action`, which is not in `PICKLIST_FIELDS_TO_EXPAND`) and step 4 (custom fields with distinct labels — Note has none). Result: **zero fields**, and `build_entity_section` renders a bare `### Note fields` header with no rows. Exactly what was observed.

This hits the `full` level too, so `add_note`, `search_notes`, and `get_notes_for_entity` all carry an empty Note field reference. The `Note.action` picklist — the 25 valid values, including the `Agent added` value that started this whole investigation — is sitting in `/meta` and never reaches the agent. That is very likely a contributing cause of the original confusion.

For the `compact` level (CR34: `search_entities`, `query_entities`, `update_record`, `get_entity_fields`), `build_entity_section` renders **only** `DEFAULT_FIELDS` names, so a missing entry yields a header-only section unconditionally. That is why both Note and CorporateUser looked empty in the generic tools.

Fix: add both entities to `DEFAULT_FIELDS` in client.py. Proposed values, every field name checked against live `/meta` for existence:

```python
"Note": "id,action,comments,dateAdded,commentingPerson,candidates,clientContacts,jobOrders,placements",
"CorporateUser": "id,firstName,lastName,name,email,phone,occupation,status,username",
```

Two names from the first draft of this proposal were rejected on verification and must not be reinstated: `departmentID` and `dateAdded` are **absent** from `/meta/CorporateUser` on this tenant. Note also that the api-quirks skill records `department` as invalid on CorporateUser queries — it kills identity resolution silently — so neither spelling belongs here.

Do not paste those blind — `DEFAULT_FIELDS` is also the read-side default for `client.get()`, so adding a `Note` entry changes what `get('Note', id)` returns (today it falls back to `fields=*`). Verify both entries with a live read-only `get()` before landing, and check the association-endpoint interaction: `_NOTE_DEFAULT_FIELDS` in server.py deliberately excludes `clientCorporation` because Bullhorn 500s on it (CR25 fix 3). The `jobOrders`/`placements` sub-selects above need the same bisect treatment described in the playbook's Symptom 6 rank 1.

Also add `action` to `PICKLIST_FIELDS_TO_EXPAND` so the 25 valid values render, which is the highest-value single line in this whole CR for agent UX.

### Bug C: the custom-field flood crowds real fields out of the 40-field cap

Even where selection "works", it works badly. CorporateUser's 30 selected fields are `status` plus 29 `customText`/`customDate`/`customFloat`/`customInt` placeholders. `id`, `firstName`, `lastName`, and `email` are absent — the fields anyone would actually need. Candidate survives only because `DEFAULT_FIELDS` seeds it first; 27 of its 40 slots still go to `customDate*`/`customFloat*` placeholders such as `customFloat23`.

Step 4 admits any custom field whose label differs from its name, and Bullhorn auto-labels every unused slot ("Custom Float23" vs `customFloat23`) so the test passes for hundreds of empty fields. The `[:MAX_FIELDS_PER_ENTITY]` cap then truncates before reaching anything useful.

Fix: tighten step 4 to exclude auto-generated labels. A label is auto-generated when normalising it (strip spaces, lowercase) equals the normalised field name — `"Custom Float23"` → `customfloat23` == `customfloat23`, so it is excluded, while a genuinely renamed field like `customText41` → `"Placement Type"` survives. Then add an explicit step 0 that always seeds `id` plus any of `firstName`/`lastName`/`name`/`email` present in `/meta`, so identity fields can never be crowded out regardless of `DEFAULT_FIELDS` coverage.

This will reduce the enrichment payload, so re-measure token cost; CR34's ~80% reduction is the baseline to compare against.
