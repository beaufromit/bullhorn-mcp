# CR43: CV flow where Claude reviews the parse before it is written

## Status: APPROVED (owner, 2026-10-02). Design decisions are the owner's (2026-09-30 to 2026-10-02); assumptions A1 to A7 resolved; D8 and D9 added at replan. PRD amended (FR-15 Amendment 2, US-50, US-51). Replanned 2026-10-02 as Sprint 41 (v0.0.54). Built and deployed together with CR44 (duplicate detection).

## Motivation

T40.8 live acceptance (v0.0.53, 2026-09-29) created test Candidate 173063 from the sample CV. The upload ticket flow and the CR42 parser fix both work, but the run exposed the rest of the CR19 CV flow as never having run in production:

1. **Skills crash.** Bullhorn returns `skillList` as plain strings (`["EXCEL", "ANNUAL BUDGET", ...]`) and the ID-matched skills separately as `primarySkills` (`[{"name": "IFRS", "id": 1000125}, ...]`). The code (CR19) assumed `skillList` was `[{id, name}]`, and `tests/conftest.py` `sample_parsed_resume` was written to match that assumption. `skill.get("id")` on a string raises `AttributeError`:
   - `create_candidate_from_cv` crashes **after** the Candidate is created (173063 got fields, description, 2 work history, 2 education; no skills, no file).
   - `attach_cv` crashes at `server.py:3116`, **before** the preview/commit split, so even a preview fails.
2. **A created record can be hidden.** `create_candidate_from_cv` only catches `AuthenticationError` / `BullhornAPIError`. Any other exception after the create loses the Candidate id, the warnings and `cv_attach_retry`; the agent had to find 173063 with a duplicate search.
3. **Claude cannot correct the parser.** The parser left `companyName` empty (it is required on this tenant, and `required_fields_missing` gives no hint), merged an employer into a job title ("Financial Accountant Sample Gadgets Ireland"), turned "Present" into a fixed end date, and matched "Python" and "Software Testing" for a finance CV. `create_candidate_from_cv` only lets Claude override Candidate fields; work history, education and skills are written raw. `attach_cv` lets Claude choose which fields to write but not correct any value.
4. **Two copies of the duplicate check.** `find_duplicate_candidates` (tool) and `_check_candidate_duplicates` (used by the create tools) use the same search and scoring but are separate code and report differently.

History (checked 2026-09-30): before CR41, consultants had Claude read the CV and call `create_candidate` directly; the CV file never got attached. `parse_cv_text` existed but always failed (CR42 root cause). CR41's non-goals deferred "how these tools interact with the existing candidate-from-CV flow" to a follow-up CR; this is that CR.

## Live evidence (read-only / parse-only, owner-approved, 2026-09-29 and 2026-09-30)

- `parseToCandidate` (file) and `parseToCandidateViaJson` (text) return the same shape: `confidenceScore`, `candidate`, `candidateEducation`, `candidateWorkHistory`, `skillList` (strings), `primarySkills` (`[{name, id}]`), `rawParsedOutput`.
- Work history entries carry `startDate`, `endDate`, `title`, `comments`; no `companyName` on this CV. Education carries `school`, `major`, `graduationDate`, or `certification`.
- Candidate 173063 after the failed run: `primarySkills` association empty, `skillSet` null, `EntityFiles` empty, 2 workHistories, 2 educations, HTML description present.
- Bullhorn REST docs: `format` is a required query parameter on both parse endpoints; `populateDescription` fills the description. The response skill shape is not documented (hence the CR19 guess).

## Owner decisions (2026-09-30)

- D1: The parser drafts, Claude reviews against the CV and corrects, and the server writes Claude's version, including work history, education and skills.
- D2: Write both skill lists: `skillSet` (free text, from `skillList`) and `primarySkills` (ID links, from `primarySkills`), after Claude's review.
- D3: **New candidates: write, then report exactly what was written.** No confirmation step.
- D4: **Updates to an existing candidate: additions apply straight away, overwrites need confirmation** (owner, 2026-10-02). Additive changes (attach the CV, add work history and education not already on the record, append free-text skills, link matched skills, fill a field that is currently empty) are written without confirmation. Replacing a field that already has a value (including the description) waits for `confirm=True` and is returned as a preview. Callers with no consultant present (skills, later automation) pass `confirm=True` on the first call, and overwrites then happen automatically.
- D5: Candidates from LinkedIn / Perplexity details (no CV) can also get work history, education and skills: `create_candidate` accepts the same optional lists.
- D6: One shared duplicate-check function behind the tool and every create path. The new matching logic is CR44, built alongside this CR and deployed with it (owner, 2026-09-30).
- D7: Generic (non-CV) upload and `attach_file` are CR45, after CR43 and CR44.
- D8 (owner, 2026-10-02, at replan): `attach_cv` drops `include_work_history`, `include_education`, `include_skills` and `force_all`. Additions always apply (D4). Claude controls each section through the list it passes: an omitted list means "use the stored parse", an empty list means "add none of this". `fields_to_update` only limits which scalar fields are considered: omitted means every parsed field (empty fields are filled now, filled ones become overwrites waiting for `confirm=True`); given means only those fields.
- D9 (owner, 2026-10-02, at replan): match outcomes are recorded through a `match_check_id`. Every CR44 match check returns one; `create_candidate`, `create_candidate_from_cv` and `attach_cv` take an optional `match_check_id` and log the outcome automatically (created new, created with `force` over a match, attached to candidate X). `attach_cv` does not run its own match check. No new tool. See CR44 D12.

## Goals

1. **Parse once, store it.** `parse_cv(upload_id)` stores the parse on the upload record (same owner binding and 30-minute lifetime as the file). Claude gets back the candidate fields, work history, education, `skillList` and `primarySkills`. The description is omitted from the response (its length is shown).
2. **Claude's corrections are what gets written.** `create_candidate_from_cv` and `attach_cv` take `fields_override`, `work_history`, `education`, `skills` (free-text names) and `primary_skills` (ids). A list Claude passes replaces the parsed one; an omitted list uses the stored parse. The description always comes from the stored parse.
3. **New candidate (D3):** `create_candidate_from_cv` writes in one call: Candidate, work history, education, `skillSet`, `primarySkills`, CV file. The response lists exactly what was written (fields, each child record with its new id, both skill lists, the file) so Claude can tell the consultant.
4. **Existing candidate (D4):** `attach_cv(candidate_id, upload_id, <same correction args>)` without `confirm=True` writes the additive changes (the file, new work history and education, appended `skillSet`, linked `primarySkills`, empty fields filled), reports them, and returns the planned **overwrites** as current vs new without writing them. The same call with `confirm=True` writes the additions and the overwrites. A confirm call after the additions does not repeat them: work history and education are already de-duplicated against the record, skills already linked or listed are skipped, and the file is not attached again. Because the first call attaches the file (which drops the bytes, NFR-9), the stored parse is kept on the upload's tombstone until the 30-minute purge so the confirm call can still use it; `upload_already_attached` no longer blocks a confirm call on the same upload.
5. **No hidden records.** Once the Candidate exists, no failure after it (in either tool, any exception type) loses the id: the response is `created: true` / `committed: true` with the id, warnings and a retry hint.
6. **LinkedIn / Perplexity (D5):** `create_candidate(fields, work_history=None, education=None, skills=None, primary_skills=None, force=False)` writes the child records and skills after the Candidate, using the same helper as goal 3, and reports what was written.
7. **One duplicate check (D6):** `find_duplicate_candidates` and every create path call one function. The create paths report its best match in the same form the tool does.
8. **Better required-field error:** `required_fields_missing` says to retry with `fields_override` (or `fields` for `create_candidate`) and, for `companyName`, to take the current employer from the CV.

## Non-goals

- **Duplicate matching logic.** Replaced by CR44 (weighted evidence match check), built alongside this CR and deployed together. CR43 only routes every create and attach path through one function; CR44 replaces what is inside it.
- Generic file upload and `attach_file` for non-CV files: CR45.
- No change to the upload ticket flow (CR41) or the parser call parameters (CR42).
- `bulk_import` is unchanged.
- No attempt to fix the parser's own extraction; Claude's review is the correction.

## PRD amendment (to approve with this CR)

**FR-15 Amendment 2: Reviewed CV parsing and candidate child records (CR43)**

- `parse_cv` shall keep the parse with the upload for its lifetime, so the write uses exactly the parse Claude reviewed.
- `create_candidate_from_cv` and `attach_cv` shall accept corrected Candidate fields, work history, education, free-text skills and matched skill ids, which replace the parsed values; the description comes from the parse.
- Creating a new Candidate (from a CV or from supplied details) shall write immediately and return a full account of what was written.
- Updating an existing Candidate from a CV shall apply additions (the file, new work history, education and skills, empty fields) immediately, and shall replace an existing value only on an explicit confirmation, which a caller with no consultant present may give up front.
- `create_candidate` shall accept optional work history, education and skills.
- Candidate duplicate detection shall be one shared function used by `find_duplicate_candidates` and all create paths.
- After a Candidate has been created, a later failure shall never hide its id.

**US-50: Claude checks a parsed CV before it is written**
As a consultant, I want Claude to check what Bullhorn's parser read from a CV against the CV itself and fix mistakes before anything is saved, so that the record, its work history, education and skills are right first time.
- **Acceptance:** for a new candidate, one write creates the Candidate with Claude's corrected fields, work history, education and both skill lists, attaches the CV, and Claude tells the consultant exactly what was written. For an existing candidate, the CV and any new information are added straight away, and Claude shows any value that would be replaced and replaces it only after the consultant confirms. A failure after the create still returns the new Candidate id.

**US-51: Add a candidate from sourced details with their history**
As a consultant, I want a candidate found through LinkedIn or a Perplexity search added with their work history, education and skills, not just their name and current role.
- **Acceptance:** `create_candidate` with work history, education and skills creates the Candidate and those records, and reports what was written.

## Changes

1. **`uploads.py`**: `_Upload.parsed: dict | None`; `set_parsed(upload_id, owner_sub, parsed)`; `get` returns `parsed`. The bytes are still dropped on attach (NFR-9); the parse (structured fields, no file) stays until the record is purged, so an `attach_cv` confirm call works after the additions call attached the file.
2. **`server.py`**
   - `_parse_upload(upload)`: return the stored parse, or parse and store it.
   - `_split_parsed_skills(parsed)` → `(free_text_names, primary_skill_ids)` from the real shape (`skillList` strings, `primarySkills` objects). Tolerates a missing key.
   - `_write_candidate_children(client, metadata, candidate_id, work_history, education, skills, primary_skill_ids, append_skillset)` → a written-records report plus warnings; each item best-effort, as today. Shared by `create_candidate_from_cv`, `attach_cv` commit and `create_candidate`.
   - `create_candidate_from_cv(upload_id=None, content=None, content_type=..., force=False, fields_override=None, work_history=None, education=None, skills=None, primary_skills=None)`. Everything after `client.create` inside a guard that turns any exception into a `created: true` response with the id (goal 5).
   - `attach_cv(candidate_id, upload_id, fields_to_update=None, fields_override=None, work_history=None, education=None, skills=None, primary_skills=None, confirm=False)` (D8: `include_*` and `force_all` removed; `match_check_id` added in CR44 Sprint 42B). **Behaviour change:** `fields_to_update` no longer triggers a write on its own; it only limits which fields go into the plan. Additions always apply; overwrites apply only with `confirm=True`. The overwrite preview is built by the same function that writes them.
   - `create_candidate(fields, force=False, work_history=None, education=None, skills=None, primary_skills=None)`.
   - `_find_candidate_duplicates(client, first, last, email)` → the tool's full result; `_check_candidate_duplicates` becomes a thin wrapper returning its best match. Logic unchanged.
   - `required_fields_missing` hint (goal 8). Tool descriptions and `request_cv_upload` `next_steps`: parse first, review, then create or attach; tell the consultant what was written; get the consultant's yes before passing `confirm=True` when a consultant is present.
3. **Tests**
   - Replace `sample_parsed_resume` in `tests/conftest.py` with the real live shape (string `skillList`, object `primarySkills`, work history without `companyName`); every CV test then runs against reality.
   - Payload-assertion tests for every new write: child records carry Claude's corrected values, `skillSet` gets the free-text names, `primarySkills` gets the ids, attach appends rather than replaces `skillSet`.
   - Stored parse is reused (parser called once across `parse_cv` then create/attach).
   - `attach_cv` without `confirm` writes the additions only (payload-asserted) and returns the overwrites; with `confirm` also writes exactly the previewed overwrites; a repeat call adds nothing twice; an empty field counts as an addition, a non-empty one as an overwrite.
   - Any exception after create returns the id (create and attach).
   - Shared duplicate function: the tool and the create path agree on the same fixture.
4. **PRD.md**: FR-15 Amendment 2, US-50, US-51 as above.
5. **README / docs**: CV flow section; IMPLEMENTATION-PLAN.md sprint row and detail; T40.8 resumes after this CR's deploy.

## Assumptions (confirm or correct)

- A1: Decided (owner, 2026-10-02). If `create_candidate_from_cv(upload_id)` is called without a prior `parse_cv`, it parses and stores the result itself and writes the parser's values plus any corrections. The three parts (parse, duplicate check, write) each stand alone so other tools and skills can call any of them; tool descriptions and `next_steps` teach the recommended order (parse, review against the CV, then write). Nothing blocks the shortcut.
- A2: **Verified live 2026-10-02 on test Candidate 173063 (owner-approved write test, skill 1000125 IFRS):**
  - The current code's method, `POST /entity/Candidate/{id}` with `{"primarySkills": {"data": [{"id": ...}]}}`, returns 200 `changeType: UPDATE` with a `WARNING ATTEMPT_TO_SET_TO_MANY` message and **writes nothing**. It would have looked like success. The same applies to `attach_cv`'s commit.
  - `PUT /entity/Candidate/{id}/primarySkills/{skillId}` returns `changeType: ASSOCIATE` and the skill appears on the record. This **adds** to existing links (so A3 holds naturally).
  - `DELETE /entity/Candidate/{id}/primarySkills/{skillId}` removed it (`DISASSOCIATE`); 173063 is back to no primary skills.
  - The build uses the association `PUT` (comma-separated ids for several, to confirm in the build with a test) and treats any response `messages` warning as a failure to report, not a success.
- A3: Holds (A2 live test): on an update, `primarySkills` are added to the existing links, not replacing them, like `skillSet`.
- A4: New-candidate creation stops on a likely duplicate unless `force=True`, using the CR44 bands and caller policy (CR44 Q3). With D3 there is no preview, which is why CR44 ships in the same deploy.
- A5: Decided (D4). The `attach_cv` trigger change is acceptable; its only live use so far is T40.8.
- A6: The overwrite preview omits the long description, showing only that it would be replaced and both lengths.
- A7: Ships as Sprint 41, tagged v0.0.54 after the review loop, but is deployed only together with CR44 (Sprint 42, v0.0.55). Afterwards T40.8 is re-run on Candidate 173063 (and one new test Candidate).
