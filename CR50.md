# CR50: File upload follow-ups from the v0.0.59 acceptance test

## Status: APPROVED (owner, 2026-11-20). Raised 2026-11-20 from the T44.8 Cowork and claude.ai runs. Sprint 46, v0.0.61, after CR49. PRD amendment applied to PRD.md 2026-11-20.

**Owner answers (2026-11-20):**
- **Q1/Q2: no default description, for any file.** Bullhorn keeps filling a file's description with its text, exactly as a UI upload does. The owner first chose the filename for all files, CVs included, then reversed that once the live survey below showed this is normal Bullhorn behaviour ("I want use to continue as normal in Bullhorn").
- **Q3: yes.** Read tools truncate file descriptions for Claude, and a new read-only tool returns one file's text in full, so no detail is out of reach ("what I don't want is details missing, when needed").
- **Q4: yes**, rename the box resource in this CR. The F1 Cowork retest covers it.
- **Q5: yes**, `already_attached` reports `_CV_FILE_TYPE`.
- **Q6:** its own sprint.

## Motivation

The v0.0.59 acceptance test (T44.8, 2026-11-20) passed in both the Cowork desktop app and a claude.ai web chat. Both reports, plus read-only checks afterwards, found problems in how the upload tools guide Claude and in how much file text reaches Claude. None blocked a step, but F1 and F2 will mislead or break real use.

## Findings and root causes

**F1. The upload box fallback is hidden from Cowork (a detection bug).** `request_file_upload` picks its third next step with `_client_supports_ui()` (`server.py:3086`). That function asks whether the client advertised the MCP Apps extension at initialize.
- In the Cowork desktop run, next_steps said "If curl fails... tell the user the file could not be sent and stop".
- So Cowork did not advertise the extension. Yet `show_upload_box` rendered in the same session: the journal shows a resource read at 15:15:47, and the owner's screenshot on 2026-11-20 shows the box in Cowork.
- `show_upload_box` itself does not gate on the check (`server.py:3313-3363`).
- The result is that in Cowork, Claude is told to give up exactly when the box would work.

**F2. File descriptions flood Claude's context.**
- **Where the text comes from.** Bullhorn fills a file attachment's Description (the Files tab column) with the file's extracted text whenever no description is given. The server sends none unless asked (`client.py:337-338`).
- **It is normal Bullhorn behaviour.** Live survey on 2026-11-20 (read-only, lengths only):

  | Record | Files | Empty | 1-500 chars | Over 500 (file text) | Median | Max |
  |---|---|---|---|---|---|---|
  | Candidate | 126 | 26 | 0 | 100 | 5,463 | 14,205 |
  | JobOrder | 3 | 0 | 0 | 3 | 4,808 | 5,272 |
  | Company | 63 | 7 | 2 | 54 | 9,643 | 62,122 |

  No consultant writes their own descriptions.
- **The failure.** When Claude reads a record's files with descriptions, it gets all of that text. `get_company(10666, fields="fileAttachments[50](...,description)")` returned about 115,000 characters and went over the tool output limit.
- **No route to the text today.** No tool returns one file's text, so a contract's wording is reachable only through that flood.

**F3. Every upload gets the CV instructions.** The `use_step` in `request_file_upload` (`server.py:3076-3085`) always describes parse_cv, create_candidate_from_cv and attach_cv. It does so even when the entity hint is a JobOrder, ClientCorporation, ClientContact, Placement or Opportunity, and even for a png or eml.

**F4. `attach_cv` does not return the file type.** `written["file"]` has only `file_id` and `name`, so Claude has to read the record back to confirm `Original CV`. `attach_file` does return `type`. There are five sites: `server.py:3843`, `4150`, `4158`, `4219` and `4228`. Of these, 4158 and 4219 are the `already_attached` ones.

**F5. `attach_file` does not echo `description`.**

**F6. Wording.**
- The same-name warning says "(file id 327798, 327802, 327809)" for several files; it should say "file ids".
- The `unsupported_file_type` refusal lists the allowed types twice, in `message` (`uploads.py:249`) and in `hint` (`_upload_error` in `server.py`).

**F7. The box resource still says CV.** `_UPLOAD_BOX_URI = "ui://bullhorn/cv-upload-box.html"` (`server.py:2519`). It was kept on purpose in Sprint 44 (P5) while the box was new in Cowork. The box has now rendered in Cowork and on the web (T44.8).

## Goals

- In Cowork, Claude is offered the upload box when curl fails.
- Claude never receives more than a short preview of any file's description from a read tool, and can always get one file's full text when it needs it.
- Bullhorn's stored data and UI behaviour are unchanged.
- `request_file_upload` next_steps match what the file is for.
- `attach_cv` and `attach_file` report what they stored.

## Non-goals

- **A default description on upload.** This was rejected (Q1/Q2). Bullhorn's own fill-in stays.
- **Work history and education near-duplicates from `attach_cv`.** Rows with no company name are not matched, and neither is "BComm Accounting" against "BComm Accounting and Finance". This is the known limit of the B10 quick fix, a matching-logic change for its own CR.
- **The upload URL in `show_upload_box`'s result.** The box needs it, and it is single use and short lived.
- **Placement files showing on the parent job.** Read back on 2026-11-20: 327800 and 327811 are on Placement 11720 and also listed on job 51437 under the same id. The server sent them to `/file/Placement/11720/raw`, so this is how Bullhorn lists Placement files. Future acceptance tests must allow for it in job file counts.
- **Downloading or parsing an existing file's binary.** `get_file_text` returns the text Bullhorn already holds in the description.

## PRD trace (applied to PRD.md 2026-11-20)

FR-24 gains two bullets, and US-56 is new. F1 is covered by the FR-15 Amendment's upload box fallback. F3 to F7 are fixes inside FR-24, the FR-15 Amendment, US-53 and US-54.

> - Read tools that return file attachments shall return at most the first 500 characters of each file's description, marked as truncated with its full length. Bullhorn's stored description is never changed.
> - `get_file_text(entity, entity_id, file_id)` shall return one attached file's full description text, in pages when it is long, so no detail is lost to the truncation.

> **US-56: Read a file's text only when I need it**
> As a consultant, I want Claude to see only a short preview of each attached file's text when it reads a record, and to fetch one file's full text when the task needs it, so that a record with many CVs or contracts doesn't flood or break the chat, and no detail is out of reach.
> - **Acceptance**: `get_company` on a company with large files returns every file with at most 500 characters of description, `description_truncated: true` and `description_length`. `get_file_text` on one of those files returns its whole text (in pages over the page size). The Files tab in Bullhorn is unchanged.

## Design

### F1: offer the upload box whatever the client advertises

Drop the `_client_supports_ui()` branch from `request_file_upload` and always give one fallback step:

> If curl fails or you cannot run shell commands, call show_upload_box(upload_id='...') so the user can drop the file into the chat. Showing the box replaces this upload URL, so do not curl the old one afterwards. If no box appears, tell the user the file could not be sent and stop. Do not paste, retype or base64-encode the file.

Log at INFO, once per session, whether the client advertised the MCP Apps extension. Log the boolean only, no token and no identity. That records which hosts advertise it. Remove `_client_supports_ui()` if nothing else uses it.

### F2: truncate file descriptions on read, and add `get_file_text`

**Truncation.** A helper, `_cap_file_descriptions(data)`, runs on every read tool's result before `format_response`. Find the exact hook point at replan, so that all of these are covered:
- `get_candidate`, `get_company`, `get_contact`, `get_job`;
- `search_entities` and `query_entities`;
- the list tools when fields include files.

Behaviour:
- It walks the result. For any `fileAttachments` value (a to-many envelope `{"total", "data": [...]}` or a plain list), each row whose `description` is longer than `_FILE_DESCRIPTION_PREVIEW = 500` gets the first 500 characters, plus `description_truncated: true` and `description_length: <n>`.
- Other fields are untouched. That includes the Candidate's own `description`, which holds the CV text on the record, and which `attach_cv` previews already handle.
- It never mutates cached data; it copies the rows it changes.

**`get_file_text(entity, entity_id, file_id, offset=0)`** is a read-only tool:
- **Entity.** It takes the same entity list as `attach_file`, and Lead is refused.
- **Source.** It reads `client.get_entity_files(entity, entity_id)` and finds the row with `id == file_id`. If there is none, it returns `file_not_found` with the record's file ids and names.
- **Return.** `{"entity", "entity_id", "file_id", "name", "type", "length", "offset", "text", "next_offset"}`. `text` is a page of `_FILE_TEXT_PAGE = 20000` characters, and `next_offset` is null on the last page.
- **No text.** An empty description returns `text: ""`, with a note that Bullhorn holds no text for this file (images, emails).
- **Docstring.** About one line: "Use when a record's file preview says description_truncated and the task needs the full text."
- **Cost.** This is tool 44. Measure the token cost with `scripts/measure_descriptions.py`.

### F3: next_steps follow the hint and the extension

- **CV extension (`CV_EXTENSIONS`), hint Candidate or absent:** the current text, with both the CV path and `attach_file`.
- **Otherwise** (a non-Candidate hint, or a non-CV extension such as png, eml or msg): only the `attach_file` path. With a hint, the step names the record: `attach_file(entity='JobOrder', entity_id=51437, upload_id='...', type?, description?)`.
- **`show_upload_box`.** Its `upload_already_received` hint uses the same rule.

### F4: `attach_cv` reports the type

Add `"type": _CV_FILE_TYPE` to `written["file"]` at all five sites, including the two `already_attached` ones (Q5).

### F5: `attach_file` echoes the description

Add `"description": <what was sent, or null>` to the success response.

### F6: wording

- **Same-name warning:** "file id 1" for one file, "file ids 1, 2" for several.
- **`unsupported_file_type` hint:** "Use one of the allowed types listed above, or convert the file (for example a .md file to .txt)." The list appears in `message` only.

### F7: rename the box resource

- `_UPLOAD_BOX_URI = "ui://bullhorn/upload-box.html"`.
- Update the tool definition's `_meta.ui.resourceUri`, the result meta, and any test or doc that names the old URI.
- The journal line will then read `MCP App resource read: ui://bullhorn/upload-box.html`.

## Tests

The test files are `tests/test_server.py` (CRLF) and the client tests as needed. The privacy plugin blocks shell reads of `tests/test_server.py` and `tests/test_client.py`, so use the Read and Edit tools.

- **F1:**
  - next_steps include the show_upload_box step with `_client_supports_ui` patched True and False (or removed).
  - The "stop" sentence follows the box sentence.
  - The INFO line appears once and carries no token.
- **F2, truncation:**
  - A `fileAttachments` envelope and a plain list both get capped at 500, with the flag and length.
  - A short description is unchanged and has no flag.
  - The Candidate's own `description` is not capped.
  - A nested result is capped, for example a search row with fileAttachments.
  - The input object is not mutated.
- **F2, `get_file_text`:**
  - Full text when it is under the page size.
  - Paging, with `next_offset` set and then null at the end.
  - `file_not_found` lists the ids.
  - Lead is refused.
  - An empty description gives `""` and the note.
  - The API error surface is uniform.
- **F3:**
  - A JobOrder hint with a docx gives no parse_cv text.
  - A png with no hint gives no parse_cv text.
  - A docx with no hint, and a docx with a Candidate hint, keep the CV path.
  - The same rule holds for `show_upload_box`'s hint.
- **F4:** every `written["file"]` site carries `type`.
- **F5:** the response carries `description`.
- **F6:** one id gives "file id 1"; two give "file ids 1, 2"; the hint does not repeat the list.
- **F7:** the tool meta and the result meta carry the new URI.

Existing tests that pin the old next_steps, fallback text or URI will need updating. Find them with Grep/Read at build.
