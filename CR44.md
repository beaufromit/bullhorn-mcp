# CR44: Candidate duplicate detection by weighted evidence (match check)

## Status: APPROVED (owner, 2026-10-02). Design by the owner (pasted 2026-09-30, from an earlier chat; summarised under Design). Investigation done read-only on 2026-09-30. Owner decisions D1 to D13 recorded. PRD amended (FR-23, US-52). Replanned 2026-10-02 as Sprint 42 (v0.0.55) and Sprint 42B (v0.0.56), after Sprint 41.

Built together with CR43 and deployed together (owner, 2026-09-30). CR43's create and attach paths call this check. The generic upload CR moves to CR45.

## Motivation

The current candidate duplicate check searches `email OR firstName OR lastName` and scores on name plus an email exact match. It is weak in both directions:

- **False negative (trigger case).** Kevin Cassidy exists three times: 90308 (2009, email and mobile), 172730 (2026-09, live) and 172742 (2026-09, soft-deleted). The two new records have empty email and mobile, so the old check treated the missing contact details as evidence of a new person. All three share the same employers (Abbey Capital, McCann FitzGerald, Deutsche International Corporate Services) and the same school (Dublin City University).
- **False positives / noise.** In T40.8, `find_duplicate_candidates` returned 30 "possible" matches on a first name alone.

CR43 makes new-candidate creation write immediately with no preview (owner decision D3), so a bad duplicate check turns straight into duplicate or blocked records. That is why this ships with CR43.

## Design (owner's, summarised; full text in the 2026-09-30 conversation)

- A **match check** that takes a candidate profile and returns likely existing candidates with a percentage, a band and a plain-English per-signal breakdown. It never writes and never decides; callers act on it.
- **Scorer:** pure functions, no I/O. **Retrieval:** builds the Bullhorn searches and fetches the pool.
- **Model:** each signal adds `log2(m/u)` points; `prior = log2(pi/(1-pi))`, `pi = 0.3/N`, `N` = live candidate count; `percentage = 1/(1+2^-(points+prior))`. All m, u, caps, thresholds in config. **A missing value counts as exactly zero.**
- **Guaranteed identifiers:** email (email, email2, email3), phone (all phone fields), LinkedIn slug (from `companyURL`). Exact match is a guaranteed match unless a guard trips (value held by more than one existing candidate; generic role mailbox or internal `@thepanel.com`; forenames clearly disagree). A tripped guard drops it to a strong signal (m 0.85, u = holders/N). Different values on both sides count slightly against (about -2).
- **Names:** forename exact / nickname / Irish-English equivalent / initial / typo-fuzzy; different forenames about -6. Surname exact or fuzzy (one edit covers O'/Mc/Mac/fada); different surnames about -5 (marriage). Swapped first/last checked first. Commonness from the name search total. A name match alone can never reach a match band.
- **Work history:** `companyName` text, normalised (lowercase, strip Ltd/Limited/plc/DAC/Group/Ireland/"The", & to "and", punctuation), word-based fuzzy match; also look for employer names inside `title`. Count distinct employers, never rows. Each shared employer counts regardless of dates, weakened by commonness (employer search total); overlapping dates add a bonus; up to 3 employers. `Candidate.companyName` is an extra employer with no dates. Stale records are not evidence against. Acronyms (PwC vs PricewaterhouseCoopers) accepted as a gap.
- **Education:** tiebreaker only, small cap; same school plus graduation year within 1, or same school alone for less; never negative; filter certifications and professional qualifications.
- **Not signals:** job title alone (small bonus within a shared employer), location, skills.
- **Retrieval:** up to five parallel searches excluding deleted: email fields, phone fields, LinkedIn slug, fuzzy surname plus first initial, one nested employer search per distinct employer (up to 3; if over 200, rerun combined with the fuzzy surname, keep the original total). Union, dedupe, then fetch work history and education for the pool in one call.
- **Output:** per candidate id, name, percentage, band (high >= 98%, low < 20%, uncertain between), breakdown with reasons, flags (guaranteed match and which identifier, guard tripped, multiple strong matches, lookup hit cutoff). All strong matches returned, ranked.
- **Match log:** JSON Lines, one line per call, daily files, 30-day retention, outcomes appended later under the same request id, for agent review and calibration.
- **Testing:** offline unit tests for every signal level, symmetry, monotonicity, caps; case fixtures (Kevin Cassidy pattern, common name, married name, shared agency contact, swapped names), synthetic per D10; mocked retrieval; manual dry-run on real CVs. **Calibration:** superseded by D10 (live aggregate counts only, then match-log outcomes).

## Investigation (read-only, 2026-09-30)

### Claims from the earlier chat

| Claim | Result |
|---|---|
| `CandidateWorkHistory` has `companyName` (free text) and `clientCorporation` (lookup); placement rows carry `placement` and `jobOrder` | **Holds** (from `/meta`). In a 200-candidate sample (1,222 rows) only 5 rows had `clientCorporation` and 5 had `placement`, so `companyName` is effectively the only employer signal. |
| `/query` on `CandidateWorkHistory` is exact only; `LIKE` rejected | **Holds.** `companyName LIKE '%Abbey%'` returns 400 `errors.cannotUseLIKE`; `companyName='Abbey Capital'` works. |
| Nested Lucene `workHistories.companyName:(abbey AND capital)` matches words, one row per candidate, total usable as commonness | **Holds.** 46 candidates; case-insensitive (`ABBEY AND CAPITAL` also 46). Phrase `"Abbey Capital"` gives 37, so word-AND is the looser, right choice. Plain `(Abbey Capital)` without AND is an OR (2,711), so AND must be explicit. |
| Fuzzy surname works (`lastName:cassidey~1` finds Cassidy), total usable as commonness | **Holds.** 69 for both `cassidy` and `cassidey~1`; with `firstName:k*` 6. |
| `candidate.id IN (...)` works on `/query CandidateWorkHistory` | **Holds** (27 rows for the three Cassidy ids; also works on `CandidateEducation`). |
| Records carry repeated work history rows | **Holds, and it is common.** 55 of 200 sampled candidates (27%) have the same employer on several rows. 90308 has 20 rows for about 8 employers, from re-parses (two dated variants of each Abbey Capital role). |
| Parser mangles fields | **Holds, worse than stated.** Seen: employer in title ("Solicitor McCann FitzGerald"), descriptive text as title ("broker agreements banking agreements..."), prefixed employer ("Corporate with Abbey Capital"), and **companyName and title swapped** (`companyName: "Account Assistant (Finance Department)"`, `title: "SSE Renewable (Airtricity Ltd),"`). 7% of rows have no companyName, 7% no title. |
| LinkedIn URL is in `companyURL` ("Personal URL"); `customText10` is legacy | **Holds.** `customText10` ("PitchMe Linkedin") is set on 1 live candidate. |

### Other findings

- **Soft-deleted candidates are in the search index.** `lastName:cassidy` returns 69, with `isDeleted:0` 68 (172742 is the difference). Every search must filter (the client already appends `isDeleted:0`).
- **Soft-deleted work history rows:** 5% of sampled rows (63 of 1,222). `/query` returns them, so the pool fetch must add `isDeleted=false`. The nested `workHistories.*` search **excludes** them (20 deleted rows checked: a hit only when a live row with the same name exists).
- **`workHistories.title` is searchable** the same way (`(abbey AND capital)` in title: 1 candidate).
- **Punctuation and accents in nested/name search:** `&` works (`a&l AND goodbody` 283). Accents fold (`padraig` = `pádraig` = 94). Apostrophes do not fold: `lastName:"o'brien"` 466 vs `obrien` 1; `companyName:(o'reilly)` 43 vs `(oreilly)` 20. Search both forms. Generic words are huge: `ireland` 16,969, `bank` 12,812, `group` 9,973, `bank AND of AND ireland` 4,640.
- **Dates:** epoch ms. Year-only dates land on 1 or 2 January (timezone shift): 27% of start dates. A null `endDate` (11%) means current. The parser writes "Present" as the parse month (1 Sept 2026 on both 2026-09 Cassidy records). `isLastJob` is never set (0 of 1,222). Date overlap should be compared at year granularity.
- **Education:** only 42% of candidates have any. 57% of rows have no school; about 20% are professional qualifications in `degree` (Chartered Accountant, ACCA, PMP, "Law Society of Ireland" in `major`); the `certification` field is almost unused (3 of 549). Confirms tiebreaker-only and the filter.
- **Phones are stored in many formats.** Top patterns in a 50-record sample: `+353XXXXXXXXX` (23), `0XX XXXXXXX` (7), `+353 XX XXX XXXX` (5), plus `(0)`, dashes, double spaces. Search is **format-exact**: `mobile:"+353857260864"` and unquoted `353857260864` find 90308; `0857260864` and `085 726 0864` find nothing; wildcards and a bare `+` are rejected (400).
- **Emails:** exact search across `email OR email2 OR email3` works. `@thepanel.com` phrase: 26 live candidates. Role mailboxes: `info@` 34, `cv@` 4, the other listed prefixes 0.
- **LinkedIn URL forms:** `/in/<slug>` and the old `/pub/<name>/<x>/<y>/<z>` form (for example `ie.linkedin.com/pub/liam-dunne/11/140/8b0`), with country subdomains, mixed case, with or without scheme or trailing slash, URL-encoded accents.

## Critique (where I disagree or would change the design)

1. **Drop the plain HTTP endpoint for now.** "Same pattern as /upload-cv" is the pattern that never worked in production: a static secret the model cannot hold and no Entra identity. n8n and local tools can call the MCP tool over the authenticated transport. Revisit with proper auth when there is a concrete caller.
2. **The match log should not store the full parsed CV.** Thirty days of full CV contents and every returned candidate's personal data on disk is a GDPR processing and retention question. Store the request id, caller, versions, the signals and values the scorer used (normalised identifiers hashed), candidate ids, points, bands and outcomes. That is enough to recalibrate, and the full record can be re-fetched by id.
3. **Input should be a candidate profile, not a parse result.** CR43 uses one function for three callers: a CV parse, `create_candidate` with LinkedIn / Perplexity details (no parse), and the `find_duplicate_candidates` tool. Define one profile shape (names, emails, phones, LinkedIn URL, current company, work history, education) and adapt each caller to it.
4. **Phone retrieval needs normalised variants.** Because search is format-exact, search the stored-style variants of each number (`+353...`, the national `0...` form, and the unquoted digits) and compare phones locally after normalising (strip spaces, dashes, brackets, `(0)`; map `00353` and `0` to `+353`; ignore anything under 7 digits). Otherwise phone matching mostly fails silently.
5. **Search employers on both `companyName` and `title`, and compare both ways,** because the parser sometimes swaps them.
6. **Be careful stripping "Ireland" and "Group".** "Bank of Ireland" becomes "bank of". Strip only as a trailing legal or jurisdiction suffix, and never down to fewer than one distinctive word. Commonness weighting should still be what handles generic employers.
7. **Normalise LinkedIn `/pub/` URLs too,** not only `/in/`. They are a real share of the 6% of candidates that have a `companyURL`.
8. **Filter soft-deleted work history and education rows in the pool fetch** (`isDeleted=false`); the nested search already does.
9. **"Value held by more than one candidate" disables the guarantee exactly when duplicates already exist.** That is fine because the output flags multiple strong matches, but the band should still be high when every holder is the same person by other signals. Let the scorer handle this; don't special-case it.
10. **Config in a versioned file in the repo** (for example `src/bullhorn_mcp/match_config.json` with a `version`), not environment variables. Calibration changes then go through the CR and review loop, and the log records which version scored each call.
11. **Scale check.** With N = 73,815 the prior is about -17.9 points, so reaching 98% without an identifier needs about +23.5. Rough placeholder values (surname u about 69/N, forename given surname, one shared employer u about 46/N) reach that for the Cassidy case, and a name match alone does not. Calibration will set the real values.
12. **Outcome reporting needs a way in.** Consultant answers ("same" / "different") need a tool, or a field on the create and attach calls. I'd put it on the calls CR43 already has (`create_candidate` / `create_candidate_from_cv` / `attach_cv` record the chosen outcome against the request id) rather than add a tool.

## Owner decisions (2026-09-30)

- D1: Phone matching uses normalised number variants for search and compares normalised numbers locally (critique 4).
- D2: Soft-deleted candidates, work history rows and education rows are ignored for matching (critique 8).
- D3: Dates are compared by year only.
- D4: Education keeps professional qualifications held in `degree` (ACCA, Chartered Accountant, ...) as one more data point to compare, not filtered out. Still a tiebreaker only, never negative.
- D5: No HTTP endpoint in this CR; n8n and other callers come later (Q1, critique 1).
- D6: Minimal match log without CV contents (Q2, critique 2).
- D7: One profile input shape for every caller (Q4, critique 3). The output echoes the normalised profile that was compared, so the consultant can see what was checked against what.
- D8: Highlighting (Q7, both):
  - (a) Soft-deleted candidates never count towards scoring, but a separate lookup flags when the profile matches one ("matches deleted candidate 172742"), for example a GDPR removal.
  - (b) Whenever there is a match, the response carries who, the percentage and the reasons, and the tool descriptions require Claude to show them to the consultant. A create never stops without explaining why.
- D9: Create-path policy (Q3). High band or a guaranteed identifier: stop with `duplicate_found` and point to the update flow. Uncertain: stop and list the candidates for the consultant to decide. Low: write. `force=True` overrides both stops.
- D10: Calibration (Q5, option 1). All test data and fixtures are synthetic; no real person's data goes in the repo, including a synthetic stand-in for the Kevin Cassidy case. Calibration reads only aggregate totals from live (name, employer and identifier holder counts), never storing or printing records. Thresholds are reasoned from those counts, then refined from match-log outcomes. No measured error rate before go-live (accepted).
- D11: Sequencing (Q6). Sprint 41 = CR43 (v0.0.54), Sprint 42 = CR44 (v0.0.55), each with its own review loop; one deploy after both. v0.0.54 is never deployed alone.
  - **Amended at replan (owner, 2026-10-02):** CR44 is too large for one ~100k-token sprint and is split. **Sprint 42** (v0.0.55): pure scorer, normalisers, name tables, versioned `match_config.json`, offline tests; not wired into any tool. **Sprint 42B** (v0.0.56): retrieval, pool fetch, wiring into `find_duplicate_candidates` and every create path, D9 policy, match log, outcomes, calibration. One deploy after 42B; v0.0.54 and v0.0.55 are never deployed.
- D12 (owner, 2026-10-02, at replan; resolves critique 12): every match check returns a `match_check_id`. `create_candidate`, `create_candidate_from_cv` and `attach_cv` accept an optional `match_check_id` and append the outcome to the match log under it automatically (`created_new`, `created_with_force` over a match, `attached_to` candidate X). `attach_cv` does not run its own check. No new tool.
- D13 (owner, 2026-10-02, at replan): US-52 gains an acceptance clause for the log and versioned config (FR-23 bullets 3 and 4 had no user story).

## Goals

1. `duplicates.py` (scorer, pure) and `duplicate_retrieval.py` (searches and pool fetch), both behind one function used by `find_duplicate_candidates` and every CR43 create and attach path (CR43 D6).
2. `find_duplicate_candidates` accepts a profile: the current name and email arguments plus optional phones, LinkedIn URL, current company, work history, education, or an `upload_id` whose stored parse is used. It returns the ranked matches with percentage, band, breakdown and flags.
3. The create paths apply the caller policy in Q3.
4. Match log per critique point 2, with outcomes recorded from the create and attach calls.
5. Tests per the design with synthetic fixtures, and calibration per D10.

## Non-goals

- No HTTP endpoint (critique 1).
- No automatic merging of existing duplicates; they are only flagged.
- No acronym matching (accepted gap).
- ClientContact and company duplicate checks are unchanged.

## PRD amendment (to approve with this CR)

**FR-23: Candidate duplicate detection by weighted evidence (CR44)**
- Candidate duplicate detection shall score existing candidates against a profile using names, contact identifiers, LinkedIn profile, employers and education, where a missing value is never evidence against a match.
- It shall return each likely match with a percentage, a band and a plain-English reason per signal, flag guaranteed identifier matches and multiple strong matches, and never write to Bullhorn.
- One implementation shall serve the duplicate tool and every candidate create and update path, and its weights and thresholds shall be versioned configuration.
- Each check shall be logged (without CV contents) with its outcome, for calibration.

**US-52: Spot a returning candidate even without contact details**
As a consultant, I want Bullhorn to recognise a candidate who is already on file from their name, employers and education, even when the new CV has no email or phone, so that I update their record instead of creating a duplicate.
- **Acceptance:** a profile matching an existing candidate on name, employers and school but with no email or phone is returned as a high match with its reasons, and the consultant is shown them; two different people sharing a common name are not; a match against a soft-deleted candidate is flagged. Each check is logged without CV contents, with its `match_check_id`, the configuration version that scored it and, once a create or attach call reports it, the outcome, so the weights can be recalibrated. (Live check uses the Kevin Cassidy 90308 pattern, dry-run only.)
