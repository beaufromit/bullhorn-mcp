# CR47: list_tearsheets uses /query/Tearsheet, not /search

## Status: APPROVED (owner, 2026-10-30, "let's just do this now"). Written 2026-10-30 from a handoff pasted by the owner. PRD amended (FR-21 Amendment, US-40). Ships BEFORE CR46: Sprint 42C, v0.0.57. CR46 moves to v0.0.58, CR45 to v0.0.59.

## Motivation

`list_tearsheets` fails on every call in production with `Unknown search entity Tearsheet`. Tearsheet is not a Lucene-indexed entity on this tenant, so `/search/Tearsheet` does not exist. The tool has been broken since it shipped in CR32 (Sprint 33, v0.0.44): its tests mock `search_with_meta` and never touched the live endpoint (the documented live-API blind spot). `get_tearsheet`, `create_tearsheet`, `add_to_tearsheet` and `remove_from_tearsheet` use `/entity` and association endpoints and are not affected.

The fix is to call `/query/Tearsheet` with a SQL-style WHERE clause, as `query_entities` already does through `client.query_with_meta`.

FR-21 and US-40 both name Lucene explicitly, so the PRD must be amended first (proposed text below, to be applied on approval):

## Goals

1. `list_tearsheets` works against the live tenant, with and without filters.
2. Paging (`limit`, `start`, `pagination.next_start`) and newest-first ordering behave as on the other list tools.
3. No other tool changes behaviour.

## Non-goals

- No change to the other four tearsheet tools.
- No change to `client.py`: `query_with_meta` already does everything needed, including the metadata-driven isDeleted gate.
- No new filters beyond name and owner (for example date ranges or isPrivate). `where` covers anything else.
- Deploy is the owner's call (step 4 of the handoff) and is not part of the build.

## Design

### Tool signature (src/bullhorn_mcp/server.py)

```python
def list_tearsheets(
    name: str | None = None,
    owner_id: int | None = None,
    where: str | None = None,
    limit: int = 20,
    start: int = 0,
    fields: str | None = None,
) -> str:
```

The Lucene `query` parameter is removed (see Q1). Clause assembly:

| Input | Clause |
|---|---|
| `name="beaus test"` | `name LIKE '%beaus test%'` |
| `owner_id=99` | `owner.id=99` |
| `where="isPrivate=false"` | `(isPrivate=false)` |
| nothing | `id>0` |

Clauses are joined with ` AND `. The call is `client.query_with_meta(entity="Tearsheet", where=..., fields=fields, count=limit, start=start, order_by="-dateAdded")`, wrapped in `_paginate_envelope(meta, start, limit)` exactly as today.

A `name` containing a single quote is rejected with `{"error": "invalid_name", ...}` before any API call, matching the existing `status` and `note_action` guards (CR39 precedent). The raw `where` is passed through untouched, as `query_entities` does.

Docstring: rewritten so the text before `Args:` carries the guidance (FastMCP drops the Examples section), including "Tearsheet is not a /search entity; filter with name, owner_id or a SQL-style where".

### isDeleted

`query_with_meta` asks `/meta/Tearsheet` whether `isDeleted` exists and appends `AND isDeleted=false` only if it does. To verify live (T47.1).
