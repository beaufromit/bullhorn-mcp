## Root causes (read-only live checks, 2026-10-06)

### B1. attach_cv fails on `editHistoryValue`; create reports junk fields

`_attach_cv` (src/bullhorn_mcp/server.py) builds `proposed_fields` from every scalar key in the parse's `candidate` block, then fetches `_ATTACH_BASE_FIELDS + proposed_fields` from the record so it can compare. The parse carries keys that are not Candidate fields:

- `editHistoryValue`: **not in `/meta/Candidate` at all** (checked live). Asking for it on GET gives the 400 the tester saw.
- `onboardingReceivedSent`: in `/meta`, but a `readOnly` SYSTEM composite.
- `address`: a writable composite; it is a dict, so `_attach_cv` already drops it, but the create path passes it through (that one is fine to write).

`_create_candidate_from_cv` sends the whole parse block to `PUT /entity/Candidate`. Bullhorn ignored the unknown and read-only keys, but `written.fields` reports the payload, so it listed `editHistoryValue` and `onboardingReceivedSent` as written.

**Fix:** one helper, `_writable_candidate_fields(metadata, fields)`, keeps only keys that are in `/meta/Candidate` and not `readOnly`, and returns the dropped key names. Both CV paths run the parse block through it before anything else, so nothing unknown reaches a GET, a plan or a write, and `written.fields` lists only what was sent. Dropped parse keys are not reported as warnings (they are parser noise, not something Claude sent); a dropped key that came from `fields_override` is reported, because Claude asked for it.

### B2. CV file never attaches: 500 DUPLICATE_VALUE on CandidateFileAttachment

`client.attach_file` sends `PUT /file/Candidate/{id}/raw?fileType=CV` with no `externalID`. 173152, 173153 and 173063 have 0 files, so the duplicate is not a second copy of the same file on that record. Every file consultants have uploaded on this tenant has an `externalID` (`General` on older "Resume" files, `Portfolio` on newer "Original CV" files, `-1` on one with no type) and an empty `fileType` (16 files on recent candidates, sampled live). No MCP attach has ever completed live: `/upload-cv` never worked and T40.8 crashed before the file step, so this code has never been proven.

**Confirmed live (T43.1, owner-approved, 2026-10-06, Candidate 173063):**

1. The v0.0.56 call (`/raw?fileType=CV`, no `externalID`): **500 DUPLICATE_VALUE**, nothing written. Reproduced.
2. Same call plus `externalID=Portfolio`: **attached**, file 326613. Read back: `type` empty, `fileType` empty. So `fileType=CV` is ignored on this endpoint.
3. `/raw?externalID=Portfolio&type=Original CV` (no `fileType`): **attached**, file 326614. Read back: `type=Original CV`, `externalID=Portfolio`, `fileType` empty, exactly like a consultant's upload.

Root cause: the missing `externalID`. **Fix:** `attach_file` sends `externalID=Portfolio` and `type=Original CV` as query parameters on the raw PUT and stops sending `fileType`. The CV paths pass these values; `attach_file` keeps them as parameters so CR45 can reuse it with other types. Unit tests pin the exact query string with respx. Files 326613 and 326614 stay on 173063 as test data.

### B3. Work history and education reported as failed although written

`_write_candidate_children` calls `client.create("CandidateWorkHistory" | "CandidateEducation", ...)`. `create()` reads the new row back with `get()`, and neither entity is in `DEFAULT_FIELDS`, so the read-back asks for `fields=*`, which this tenant rejects (`errors.allFieldsNotAllowed`, reproduced live on row 473775). The PUT had already written the row, so the exception turned a success into a warning and an empty `written` list. This is the same pattern as CR17 (JobSubmission) and CR37 (Note).

**Fix:** add `CandidateWorkHistory` and `CandidateEducation` to `DEFAULT_FIELDS` with fields verified live today:
`id,candidate,companyName,title,startDate,endDate,isLastJob` and
`id,candidate,school,degree,major,certification,graduationDate,startDate,endDate`.
A comment marks both as load-bearing for the CV write path, as the `Note` entry is.

### B4. match_check_id passed in is not carried through

In `_create_candidate_from_cv` and `create_candidate`, a passed `match_check_id` is used only when `force=True`. Without force, the tool runs a fresh check and logs the outcome under the new id; the id Claude passed is dropped. Tested: `mc_e5cf...` passed, `mc_75b6...` returned and logged.

**Fix:** see Q3. Recommended: still run the fresh check (records can change between calls), and log the outcome under **both** the passed id and the new one, so both checks are closed in the log. The response keeps `duplicate_check` (with its own new id) and adds `match_check_id` = the id passed in.

### B5. create_candidate hides the check when it creates

`create_candidate` runs the check but returns only the Bullhorn create result. `create_candidate_from_cv` returns `duplicate_check`; `create_candidate` does not. **Fix:** return `duplicate_check` on every create (null with `force=True`, as the CV path does).

### B6. Upload box does not appear in Cowork

Research (web, 2026-10-06, sources below). Anthropic says MCP Apps render on web, desktop and Cowork, custom connectors included, with no admin toggle; Desktop asks "Allow / Always allow" the first time an app displays. In practice there are many open reports of correct servers showing text only (claude-ai-mcp issues #165, #471, #729, #236 Cowork 3P mode, #1085 Cowork mobile opened 29 Sep). The closest in time, #1069 (23 Sep), was a remote feature-flag change that stopped Desktop passing `_meta.ui` through for local servers with no app update. So host behaviour can change under us.

FastMCP 3.2.4's output was checked against the current spec and matches: tool `_meta.ui.resourceUri`, resource mimeType `text/html;profile=mcp-app`, `_meta.ui.csp/domain/prefersBorder` on both list and read, protocol version `2026-01-26`. One gap: the `tools/call` **result** carries no `_meta.ui.resourceUri`, which one reporter needed (ext-apps #671).

Likely causes, ranked, with the cheapest test:

1. **The host never mounted the view** (Cowork or a flag change). Test: same prompt in claude.ai web chat and Desktop chat, not Cowork. If those render, the cause is the host and we cannot fix it in code.
2. **No `resources/read` of `ui://bullhorn/cv-upload-box.html`** (stale tool cache or a failed read). Test: server log at the call time; if missing, reconnect the connector and retry.
3. **`domain` hash mismatch.** Claude requires `sha256(<connector URL exactly as configured>)[:32].claudemcpcontent.com`. Ours hashes `{MCP_BASE_URL}/mcp`; a trailing slash or a different URL in Customize > Connectors breaks it. `domain` is optional, and the box needs no stable origin. Test: compare the hash with the configured URL.
4. **View mounted at zero height, or the handshake failed.** Test: Desktop Developer Mode, DevTools on the nested iframe.
5. **No `ui.resourceUri` on the call result.** Anecdotal.

Plan: **T43.0 diagnose before coding** (owner, about 15 minutes, no writes): run tests 1 to 4 with server logs open. Then fix what the evidence points to (Q6). Code changes that are cheap and harmless either way and go in regardless: add `_meta.ui.resourceUri` to the `show_cv_upload_box` result (5), and log `resources/read` of the box URI at INFO so the next failure is visible in the logs. If cause 1 is confirmed, there is no code fix: the box stays (D2), the docs say curl is the main route, and we report the issue to Anthropic.

**T43.0 result (owner, 2026-10-07):** claude.ai web chat and Desktop chat behave the same as Cowork: the tool card shows the request and response, the host tells the model "This tool call rendered an interactive widget in the chat", and nothing visible appears. So the host does mount our app (causes 1 and 2 ruled out), and the problem is inside the box.

- **Cause 3 ruled out:** the connector URL is `https://mcp.thepanel.com/mcp`, and `upload_url` shows `MCP_BASE_URL` is `https://mcp.thepanel.com`, so the `domain` we declare (`8b033b271394feeafd205db9b9cd21d9.claudemcpcontent.com`) is the one Claude expects.
- **Root cause (high confidence, checked against the spec's `spec.types.ts`):** `upload_box.html` sends `ui/initialize` with `clientInfo` and `capabilities`, but the spec requires `appInfo` (with `appCapabilities` and `protocolVersion`). A host that validates the request rejects it; the box swallows the rejection ("host without the bridge: nothing else to do"), so it never sends `ui/notifications/initialized` or a size, and stays at zero height. That matches "rendered" with nothing visible.
- **Second spec bug:** the box's `ui/message` sends `content` as one object; the spec requires an array of content blocks. This would have failed silently after an upload.
- **10-second expiry: not a bug.** `expires_at` was `2026-10-07T12:26:31+00:00`, 15 minutes after the call. It is UTC, which is 13:26 in Ireland, so the time looks wrong if read as local time. The response will also give `expires_in_seconds` so it can't be misread.

**Fix:** send `appInfo` per the spec; on an initialize failure show a visible error and still report a size, never stay blank; report a size on load; send `ui/message` content as an array; add `_meta.ui.resourceUri` to the result and INFO logging of the resource read (cheap extras). Tests: parse `upload_box.html` and assert the `ui/initialize` params carry `appInfo`, `appCapabilities` and `protocolVersion`, and that `ui/message` content is an array. If the box is still blank after deploy, the next step is Desktop DevTools (Developer Mode is under the app menu Help > Troubleshooting).

Sources: claude.com/blog/interactive-tools-in-claude; claude.com/docs/connectors/building/mcp-apps/getting-started and /troubleshooting; github.com/anthropics/claude-ai-mcp/issues/165, 236, 274, 471, 729, 1069, 1085; github.com/modelcontextprotocol/ext-apps specification/draft/apps.mdx and issues/671; gofastmcp.com/apps/low-level.

Separately, the tester saw `expires_at` "about 10 s later". `reissue_token` sets a fresh 15-minute window (`_issue_token`), so the code cannot produce a 10-second expiry; this needs the raw response from the retest before anything is changed. Re-issuing **does** invalidate the URL from `request_cv_upload`: only the token hash is stored, so `show_cv_upload_box` mints a new token and drops the old one (by design, CR41). The box's `message` and the `request_cv_upload` fallback step will say so, so Claude does not curl the old URL afterwards.

## Owner decisions already given (handoff)

- **D1.** A newer CV that changes the current company is a real update: `companyName` is treated like `occupation`, listed in `pending_overwrites` and written on `confirm=True`. Test 4.2 expects occupation AND companyName. Implementation detail: if the parse's `candidate` block has no `companyName`, `attach_cv` proposes the employer of the current work history entry (no `endDate`, latest `startDate`; Claude's corrected `work_history` when given). `create_candidate_from_cv` does the same when `companyName` is missing, which also stops the `required_fields_missing` round trip. **T43.2 (real parse of `tests/fixtures/sample_cv/cr41_test_candidate.docx`, 2026-10-06, saved as `tests/fixtures/cv_parse_sample.json`):** the parse's `candidate` block has **no `companyName`**; its keys are `name, address, occupation, mobile, firstName, lastName, email, description, onboardingReceivedSent, editHistoryValue` (`editHistoryValue` is a string, which is why the scalar filter let it through). Work history `companyName` is null on both entries, with the employer merged into `title` ("Financial Accountant Sample Gadgets Ireland"), and the ongoing role's `endDate` is set to about the parse date (2026-10-01), not null. So the "current entry" is the one with the latest `startDate` (ignoring `endDate`), and its `companyName` is used only when filled. With Claude's corrected `work_history` that is the corrected employer; from the raw parse it is usually nothing, so no `companyName` is proposed.

## Goals

1. `attach_cv` and `create_candidate_from_cv` send, read and report only real, writable Candidate fields.
2. A CV file attaches on create and on `attach_cv`, and `get_cv_upload` then shows `attached`.
3. Every write report matches a read-back of the record exactly (fields, work history, education, skills, file).
4. Every outcome is logged under the `match_check_id` that was passed in; every create returns its `duplicate_check`.
5. The upload box appears in Cowork in the Claude desktop app and a dropped file shows `received`.

## Non-goals

- No generic (non-CV) upload or `attach_file` tool: that is CR45.
- No scoring change apart from Q5 (D4).
- No change to the parser's name split ("Alpha" surname with "Crfortythree" middle name). It is parser quality, noted as a known risk.
