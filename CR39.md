# CR39: Escape apostrophes in CorporateUser lookups instead of rejecting them

## Status: APPROVED (owner, 2026-09-23). Assumptions A1 to A3 confirmed. PRD amended (FR-2, FR-12). Next: replan.

## Motivation

CR36 (Sprint 37, v0.0.48) added single-quote guards to the three places that interpolate a string into a Bullhorn `/query` WHERE clause. It chose **reject** for all three. The Sprint 37 review logged this as m3: on an Irish tenant, reject-only locks out real people.

- `resolve_owner("Tracey O'Neill")` raises `ValueError` before any lookup, so `create_contact`, `create_job`, `create_candidate`, `search_emails` (`user`) and `bulk_import` rows cannot take an apostrophe name as the owner.
- `resolve_caller` raises `IdentityResolutionError` for an apostrophe in the Entra email claim, which blocks every write path that relies on auto-owner.

The old code (pre-v0.0.48) was also broken for these inputs (malformed query, 400), so this is a long-standing gap that CR36 made explicit rather than a regression.

## Live evidence (read-only, 2026-09-23)

- The tenant has three CorporateUsers with apostrophe names: Tracey O'Neill (145098), Conor O'Reilly (124161) and Louise O'Leary (124148). All three currently have `isDeleted: true`, so **no active user is affected today**. The next O'Something hire would be. No CorporateUser email contains an apostrophe.
- Bullhorn `/query` accepts the SQL-style **doubled quote** as an escape: `name='Tracey O''Neill'` with `exclude_deleted=False` returns exactly id 145098. The same holds for `lastName='O''Neill'`.
- Backslash escaping (`O\'Neill`) and the raw quote both return 400 `errors.badSearchQuery`.
- The apostrophe stored in `name` is ASCII U+0027. The typographic `’` (U+2019), which Word and Outlook often insert, was not tested and would not match. This is out of scope; see Non-goals.

## Goals

1. `resolve_owner` resolves names that contain `'` by escaping them (`'` becomes `''`) instead of rejecting them.
2. `resolve_caller` resolves emails that contain `'` the same way.
3. Injection stays impossible: after escaping, the value cannot close the string literal.

## Non-goals

- `get_job_submissions(status=...)` and `list_placements` keep **rejecting** quotes. Their values are picklist statuses, which never contain apostrophes, so rejecting there is correct.
- No normalisation of U+2019 to U+0027 (possible follow-up if it bites).
- No changes to `/search` (Lucene) paths.
- No change to the error codes (`owner_not_found` / `user_not_found`) apart from what follows naturally: once the reject branch in `resolve_owner` is gone, review findings m1 and m2 no longer apply.

## Changes

1. **`client.py`**: add a small module-level helper, `_escape_where_literal(value: str) -> str`, which returns `value.replace("'", "''")`. In `resolve_owner`, replace the quote `ValueError` with `where=f"name='{_escape_where_literal(owner)}'"`. The docstring `Raises:` stays as-is and becomes accurate again.
2. **`identity.py`**: remove the quote `IdentityResolutionError` guard and use `where=f"email='{_escape_where_literal(email)}'"`, importing the helper from `client`.
3. **Tests** (update the two CR36 rejection tests; do not just add new ones):
   - `tests/test_client.py::test_owner_with_single_quote_raises` becomes a respx test. It asserts that the outgoing `/query/CorporateUser` request's `where` param is exactly `name='Tracey O''Neill' AND isDeleted=false` (check the exact isDeleted suffix against the existing tests) and that the resolved `{"id": ...}` is returned.
   - `tests/test_identity.py::test_email_with_single_quote_raises` becomes the equivalent check on `where=email='o''brien@x.com'`, with a resolved caller.
   - New: an injection attempt, such as the owner `x' OR name like '%`, produces a single, fully escaped literal in the `where` param.
   - Roughly +1 test net (719 to about 720).
4. **PRD.md**: add one sentence each to FR-2 (owner by name) and FR-12 (identity resolution): "Names and emails containing apostrophes (e.g. O'Brien) shall resolve; values are escaped, not rejected."
5. **Docs**: set CR36.md goal 2 and its resolve_owner/resolve_caller lines to "superseded by CR39", and update IMPLEMENTATION-PLAN.md with the sprint row and detail.

## Assumptions (confirm or correct)

- A1: Escape both `resolve_owner` and `resolve_caller`. CR36 argued an apostrophe in an email claim is "more likely hostile". With escaping, a hostile claim can only fail to match, so rejecting adds nothing.
- A2: This ships as a small standalone sprint before CR38 (Perplexity) and gets tagged v0.0.49 after the review loop. The Sprint 38 number stays with CR38; CR39 slots in as a patch sprint.
- A3: Only the ASCII apostrophe is handled (see Non-goals).
