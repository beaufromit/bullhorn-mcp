# CR45: Generic file upload and attach_file for non-CV documents

## Status: APPROVED (owner, 2026-11-11). Written 2026-10-06. D1 to D6 decided by the owner the same day; D7, the attached-record fields and the PRD amendment (FR-24, NFR-9 Amendment, US-53, US-54) approved 2026-11-11. **Ships after CR46** (v0.0.56 acceptance fixes, Sprint 43, v0.0.58; CR47 took v0.0.57). Target: **Sprint 44, v0.0.59**.

## Motivation

CR41 replaced base64 file arguments with upload tickets, but only for CVs, and CR43 built the reviewed CV flow on top of them. Every path that takes an `upload_id` parses the file as a CV and attaches it to a **Candidate**. Since CR41 there has been no way to attach a file without parsing it. CR41 removed the only path that did (`/upload-cv`), and CR43 D7 deferred the generic case to this CR.

What consultants cannot do today:

- Attach the letterheaded JD (built by the new-job-setup skill) to its **JobOrder**.
- Attach a fee agreement or contract to a **ClientCorporation**.
- Attach a cover letter, references, a formatted CV, a signed contract, proof of ID or a visa to a **Candidate** without it going through the CV parser.
- Attach anything to a **ClientContact**, **Placement** or **Opportunity**.

## Live evidence (read-only, 2026-10-06)

1. **Entities that take files.** `/entityFiles/{entity}` accepts: Appointment, Candidate, JobOrder, ExpenseSheet, Timesheet, BillingSyncBatch, MessageTemplate, Timecard, Placement, ClientContact, Opportunity, BillableCharge, ExpenseSheetEntry, CandidateAssessment, ClientCorporation. **Lead is not accepted** (no `LeadFileAttachment` entity either).
2. **The attachment category is the `type` field, and there are two picklists.** In the Bullhorn UI this column is labelled **"File Type"** (owner screenshot, 2026-11-11); the API field `fileType` is a different, unused field (item 6).
   - Candidate, JobOrder, ClientContact, Placement and Opportunity share one list, the system setting **`fileTypeList`**: `Original CV`, `Formatted CV`, `Cover Letter`, `References`, `Signed Contract`, `Proof of ID`, `Visa`.
   - ClientCorporation has its own list, the system setting **`clientCorporationFileTypeList`**: `Fee Agreement`, `Directions`, `Contract`, `Credit Check`.
   - Both are read live with `GET /settings/fileTypeList,clientCorporationFileTypeList`, and the same values come back from `/meta/{Entity}FileAttachment`. Admins edit them in Admin > System Settings (Bullhorn KB, File Attachment FAQ). Because `fileTypeList` is shared, a new value appears on candidate, contact, job and placement files alike.
   - `type` is a String (max 50) and is not required. `fileType` is a separate String field (max 15).
3. **How real files are labelled.** Files on the 40 newest candidates (42 files): `type` = `Resume` 21, `Original CV` 18, none 3 (`Resume` is not in today's picklist, so it is a legacy value). `fileType` is empty on all of them. On 182 open jobs, only 4 have a file, all `.docx` with no `type`. On 40 companies, 5 files: `Contract` 4, none 1. Contacts and placements: none.
4. **How to attach with a label, proven live by CR46 T43.1 (Candidate 173063, 2026-10-06).** On `PUT /file/{entity}/{id}/raw`: without `externalID` the call fails with **500 DUPLICATE_VALUE**; with `externalID=Portfolio` it attaches; `type=Original CV` as a plain query parameter sets the label; `fileType` is ignored. CR46 fixes `client.attach_file` to send `externalID` and `type`, so CR45 builds on that rather than on the v0.0.56 code.
5. **T44.1 run early (owner-approved, 2026-11-11), raw `PUT /file/{entity}/{id}/raw` on test records:**
   - JobOrder 51437, `externalID=Portfolio`, `description=...`: attached (file 327510). `description` as a query parameter is stored. Without it, Bullhorn fills `description` with the file's extracted text.
   - The same file name again on 51437: attached as a second file (327511). Bullhorn allows same-name duplicates.
   - ClientCorporation 10666, `type=Contract`: attached (file 896), `type=Contract`.
   - ClientCorporation 10666, `type=Cover Letter` (not on the company list): **attached and stored as `Cover Letter`** (file 897). Bullhorn does not check the label against the picklist, so Goal 3's check must be ours.
   - ClientCorporation 10666 with no `externalID`: attached (file 898), `externalID` empty. The DUPLICATE_VALUE seen on Candidate did not happen here; `attach_file` still always sends `externalID=Portfolio` to match consultant uploads.
   - All five files stay on the test records as test data.
6. **Field names (`/meta`, 2026-11-11).** `type` (label "Type", String 50, 100 on ClientCorporation) is the category picklist. `fileType` (label "File Type", String 15) exists on Candidate and JobOrder attachments but **not** on ClientCorporation, is empty on every real file seen, and is ignored by the raw PUT. `fileSize` (Integer) is on each attachment entity but is not returned by `/entityFiles`.

## Goals

1. **One upload ticket system for any file.** The ticket, the upload URL, the curl route, the upload box, the 10 MB cap, the 15-minute ticket and 30-minute file purge (NFR-9) and the "bytes never in a tool argument" rule all stay as CR41 built them. Only the names and the allowed file types widen.
2. **`attach_file(entity, entity_id, upload_id, type=None, description=None)`** attaches the uploaded file to a record without parsing it, under its original name. The response confirms the record, the file id, the name and the `type` written.
3. **`type` is checked against the entity's own list** from the `fileTypeList` / `clientCorporationFileTypeList` settings (cached like the note-action picklist). An invalid value is refused with the valid list, so a company file can't be labelled `Cover Letter` and a job file can't be labelled `Contract`.
4. **The CV tools keep working on CV files only.** `parse_cv`, `create_candidate_from_cv` and `attach_cv` refuse an upload whose extension isn't a CV type, with a hint to use `attach_file`.

## Non-goals

- No parsing, text extraction or content checks on non-CV files.
- No delete, rename or re-label of existing attachments. Attach only (NFR-1).
- No attachments on Lead (Bullhorn doesn't support them) or on timesheet, billing, appointment or template entities.
- No change to how CV corrections or duplicate checks work (CR43, CR44).
- No change to the new-job-setup skill itself. It is an org skill outside this repo; once `attach_file` ships, the owner updates it to attach the JD.
- No file privacy or sharing settings (`isPrivate`, `usersSharedWith`).

## Decisions for the owner

- **D1: Tool names.** (a) Rename the three tools to `request_file_upload`, `get_file_upload` and `show_upload_box`, with no aliases. One upload system with one set of names, and the tool count goes from 42 to 43 (only `attach_file` is new). (b) Keep the CV names and add generic ones: 46 tools and more description tokens (NFR-8). (c) Keep the CV names for everything and add only `attach_file`: 43 tools, but "cv" in the name of a tool that uploads a JD is misleading. Cost: the CV tool descriptions, `next_steps` text, README, PRD and any Cowork skill or prompt that names the old tools must change in the same release. **DECIDED (owner, 2026-10-06): (a), rename with no aliases.**
- **D2: Allowed file types.** Today: `pdf, doc, docx, rtf, odt, txt, html, htm`. **DECIDED (owner, 2026-10-06):** `attach_file` accepts those plus images (`png, jpg, jpeg`) and email files (`msg, eml`). Spreadsheets (`xls, xlsx, csv`) and slides (`ppt, pptx`) are not added. `zip`, executables, scripts and `heic` are refused.
- **D3: Entities.** **DECIDED (owner, 2026-10-06):** all six: Candidate, ClientContact, ClientCorporation, JobOrder, Placement, Opportunity. Lead is refused with a message that Bullhorn doesn't allow files on leads, suggesting the person's contact or candidate record instead.
- **D4: `type` when not given.** **DECIDED (owner, 2026-10-06): optional.** When no label fits, the file goes on with `type` empty, as the 4 existing job files are. The tool description tells Claude to pick the label that matches the document and to leave it blank rather than force a wrong one.
- **D5: Fix the CV label.** **Moved to CR46** (owner chose yes; CR46 Q1). CVs from the CV tools attach as `type=Original CV` with `externalID=Portfolio` from v0.0.58. CR45 changes nothing on the CV attach. A formatted CV goes through `attach_file` with `type="Formatted CV"`.
- **D6: A JD label for jobs.** The shared `fileTypeList` has no value for a job description, and adding one would also show it on candidate, contact and placement files. **DECIDED (owner, 2026-10-06): no.** JDs go on jobs with no `type`. If a value is added later, the server picks it up live with no code change.
- **D7: Same file attached twice.** **DECIDED (owner, 2026-11-11): attach anyway and warn, matching on file name only.** Bullhorn allows same-name duplicates (T44.1), and a re-sent JD is often a new version under the same name. `/entityFiles` does not return `fileSize`, so size is not compared.

## Assumptions (confirm or correct)

- A1: The upload ticket's `candidate_id` hint becomes an optional `entity` and `entity_id` hint. It is only echoed back, never enforced (as `candidate_id` is today).
- A2: The open-upload cap (10 per user), the 15-minute ticket and the 30-minute file purge apply to all files alike.
- A3: The upload route (`POST /upload/{token}`) is unchanged apart from the wider extension list.
- A4: `attach_file` takes the upload's claim for the length of its Bullhorn write (as `attach_cv` does), marks the upload `attached`, and drops the bytes.
- A5: `attach_file` uses the raw upload with `externalID=Portfolio` and `type` as query parameters, as CR46 proved on Candidate. **Confirmed on JobOrder and ClientCorporation by T44.1 (2026-11-11).**

## Design

### `uploads.py`
- `ALLOWED_EXTENSIONS` becomes the D2 list: the CV types plus `png, jpg, jpeg, msg, eml`. A new `CV_EXTENSIONS` holds the current eight; the CV tools check against it.
- `candidate_id` on the record becomes `entity` and `entity_id` (A1). **DECIDED (owner, 2026-11-11):** `created_candidate_id` and `attached_candidate_id` stay unchanged for the CV paths (the Sprint 41 C1 fix depends on `created_candidate_id`). New `attached_entity` and `attached_entity_id` fields are added beside them and set by every attach, so an upload attached to a job is not mistaken for one attached to a candidate.
- The module docstring and error messages say "file", not "CV".

### `client.py`
- `attach_file` as CR46 leaves it (sends `externalID` and `type` on the raw PUT), plus `description` as a query parameter (T44.1 proved it is stored). Never sends `fileType`.
- `_guess_content_type` covers the D2 extensions.
- `get_file_types(entity)`: the allowed labels from `GET /settings/fileTypeList,clientCorporationFileTypeList` (ClientCorporation uses the second, every other entity the first), fetched once and cached for the session. A failed read does not block an attach with no label; an attach with a label then fails with a clear message rather than writing an unchecked value.

### `server.py`
- D1 renames, with descriptions and `next_steps` rewritten for any file. The `next_steps` say which tool comes next: `parse_cv` and the CV tools for a CV going on a Candidate, `attach_file` for anything else.
- New `attach_file` tool, with error codes in the existing upload-error form: `unsupported_entity` (with the D3 list), `invalid_file_type_label` (with that entity's picklist), `record_not_found`, plus the upload errors.
- `parse_cv`, `create_candidate_from_cv` and `attach_cv` refuse non-CV extensions with `not_a_cv_file` and a hint to use `attach_file`.

### `upload_box.html`
- The wording changes from "CV" to "file". The behaviour is unchanged.

## PRD amendment (approved 2026-11-11, applied to PRD.md 2026-11-13)

**FR-24: Attach Files to Records (CR45)**

- Files of the allowed types shall be uploaded through the same single-use ticket flow as CVs (FR-15 Amendment), renamed for any file, and never passed as file contents in a tool argument.
- `attach_file(entity, entity_id, upload_id, type?, description?)` shall attach an uploaded file, without parsing it, to a Candidate, ClientContact, ClientCorporation, JobOrder, Placement or Opportunity, under the file's original name.
- A `type` label is optional. If given, it shall be one of the values Bullhorn allows for that entity's attachments, read from the tenant's file type settings; any other value shall be refused with the allowed list.
- The CV tools shall accept only CV file types and shall point to `attach_file` for anything else.

**NFR-9 Amendment:** the allowed file types for uploads become `pdf, doc, docx, rtf, odt, txt, html, htm, png, jpg, jpeg, msg, eml`; the CV tools keep the CV subset. All other NFR-9 rules (single use, 15-minute ticket, hashed token, owner binding, memory only, 10 MB, deleted on attach, 30-minute purge) apply to every file.

**US-53: Attach a job's JD to the job**
As a consultant, after Claude builds the letterheaded JD for a new job, I want Claude to attach it to the JobOrder, so the JD is on the job in Bullhorn without me uploading it by hand.
- **Acceptance:** Claude uploads the JD with the ticket flow and calls `attach_file(entity="JobOrder", entity_id=<job>, upload_id=...)`. The file shows on the job under its original name. `get_file_upload` reports `attached`. No base64 appears in the conversation.

**US-54: Attach a document that isn't a CV**
As a consultant, I want to attach a cover letter, reference, contract, fee agreement or similar document to the right candidate, contact, company or placement, so that it's on the record without being run through the CV parser.
- **Acceptance:** `attach_file` attaches the file with the `type` I ask for when it's valid for that record (for example `Cover Letter` on a Candidate, `Fee Agreement` on a ClientCorporation). An invalid label is refused with the allowed list. A Lead is refused with a clear message. Nothing is parsed, and no Candidate fields change.

## Risks

- **Renaming tools breaks anything that names them.** That includes Cowork skills and saved prompts, and the acceptance prompts for v0.0.56 and CR46's retest (they use `request_cv_upload`). Mitigation: rename in one release, after CR46's retest has passed, and list every place to update in the release notes.
- **CR46 is still changing the same code.** It reworks `client.attach_file`, the CV write paths and the upload box (B6). CR45's replan must start from the code CR46 ships, not from this draft's reading of v0.0.56.
- **Sensitive files.** `Proof of ID` and `Visa` files carry personal data. They are deleted from the server on attach, as CVs are (NFR-9), and nothing is logged beyond the name and size.
