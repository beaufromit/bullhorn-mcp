# CR41: CV file intake via upload tickets (replaces /upload-cv and base64 inputs)

## Status: APPROVED (owner, 2026-09-29). Sprint 40 (target v0.0.52). T40.1 hands-on test PASSED 2026-09-29. BUILT 2026-09-29 (819 tests, 42 tools), awaiting /review; T40.8 live acceptance waits on deploy. Build notes and decisions in IMPLEMENTATION-PLAN.md Sprint 40.

## Motivation

Consultants add candidates from a CV. Claude extracts the details fine, but getting the file itself onto the Bullhorn record does not work:

1. **Base64 through the model is unusable.** `parse_cv`, `create_candidate_from_cv` and `attach_cv` take `file_b64: str`. A tool call is JSON the model writes token by token, and base64 costs roughly 1.4 characters per token, so a 150 KB CV is about 100k output tokens. This is the slowdown consultants saw.
2. **`POST /upload-cv` (CR27) has never worked in production.** It is guarded by one static `UPLOAD_SECRET` that the model cannot safely be given. Its create path also calls `create_candidate_from_cv` from a plain HTTP handler, where there is no Entra access token in context, so `resolve_caller()` for owner stamping is very likely to fail (probable root cause, not reproduced; the owner chose to replace the endpoint rather than debug it).

3. **`UPLOAD_SECRET` was never set in production.** Found in the T40.1 hands-on test (2026-09-29): a POST to `/upload-cv` returned `upload_secret_not_configured` (HTTP 400), so the endpoint rejected every request.

### Research summary (2026-09-29)

- MCP has no file type. SEP-2356 (declarative file inputs) was closed 2026-08-23 in favour of **SEP-2631 "File Objects and Transfer"** (open draft, last updated 2026-09-26), which standardises presigned upload URLs (`files/authorizeUpload`). It is not in the 2026-07-28 spec and no host implements it yet.
- The current industry pattern is an **upload ticket**: a tool mints a short-lived single-use URL, whoever holds the bytes posts them there directly, and a second tool reads the result. SEP-2631 formalises the same shape, so this design migrates cleanly later.
- **Cowork puts chat attachments on disk in its VM**, readable by Claude's shell. Owner test on 2026-09-29: `find / -name '*.docx' -path '*upload*'` found the attached file, and `curl -sI https://mcp.thepanel.com/mcp` reached the server (HTTP 401 via Caddy, as expected with no token). So Claude in Cowork can `curl` an attached file straight to our server with no re-selection by the user.
- MCP Apps (Claude, since 2026-01-26) can render an upload box inside the chat. An app-only tool or a direct `fetch` from the iframe carries the bytes without the model.

## Goals

- A consultant attaches a CV to a Cowork chat once, says "add this candidate" (or "attach this CV to Jane"), and the file lands on the Bullhorn record. No base64 in the conversation, no re-selecting the file.
- If Claude cannot send the file itself (network blocked, no shell), the fallback happens **in the same chat** (owner requirement: no separate web page).
- Remove the broken `/upload-cv` endpoint, `UPLOAD_SECRET`, and the `file_b64` inputs outright.

## Non-goals

- No browser upload page (owner rejected "Route C": sending users to a separate tab).
- No SEP-2631 support now. Revisit once FastMCP and Claude ship it.
- No persistent upload storage (disk, S3). In-memory with a short TTL is enough for a one-conversation handoff.
- No change to `parse_cv_text` (pasted text path) or to the Bullhorn parse/attach client methods.
- No paste-the-text fallback inside the upload flow (owner decision). How these tools interact with the existing candidate-from-CV flow is reviewed in a follow-up CR once uploads work.
- No support for stdio mode uploads. Stdio has no HTTP listener; the new tools return a clear error there.
- Fixing the RFC 6750 cosmetic issue seen in the owner's test (a request with no token gets `error="invalid_token"`) is out of scope. It lives in FastMCP's auth layer; logged for later.

## Assumptions (confirm or correct)

1. **`file_b64` is removed completely**, not kept as a fallback (owner approved 2026-09-29). Keeping it invites the model back onto the slow path. Consultants use Cowork exclusively.
2. Production runs as **one process** (`bullhorn-mcp.service`, single uvicorn worker), so an in-memory store is shared by the MCP tools and the upload route. A service restart drops in-flight uploads; the user just re-runs the step.
3. The public base URL for upload links comes from the existing `MCP_BASE_URL` env var (already required in HTTP mode). No new URL config.
4. Max upload size **10 MB**, because that is Bullhorn's own cap on record file attachments ([Bullhorn File Attachment FAQ](https://kb.bullhorn.com/ats/Content/BHATS/Topics/fileAttachmentFAQ.htm): "The maximum file size for attachments in Bullhorn is 10 MB"). Anything larger would pass our server and then fail at Bullhorn, so we reject it up front with a clear message. Allowed extensions `pdf, doc, docx, rtf, odt, txt, html, htm`.
5. `mcp.thepanel.com` is **already** in Cowork "Additional allowed domains" (owner confirmed 2026-09-29), with egress on "Package managers only". The owner's HEAD test passed with that setting, so the allowlist works on this tenant despite anthropics/claude-code#38984. T40.1 confirms with a real POST; "All domains" is the fallback only if the POST is blocked.
6. Whether Cowork renders MCP Apps is **unverified**. T40.1 is a spike that proves it before Route B is built.
7. **Filenames.** Cowork adds a few random characters to the start of attached files' names in its VM. The model sees the original name in the chat, so it passes that name to `request_cv_upload(filename=...)` and the server stores it on the ticket. The name sent by curl is ignored, except that its extension must match. The file lands in Bullhorn under the original name. T40.1 records the actual prefix pattern; if the model turns out not to know the original name, the server strips the prefix instead (pattern-based, only once the pattern is confirmed).

## Design

### The flow (one ticket system, two ways to deliver the bytes)

```
request_cv_upload(candidate_id?)  ──►  { upload_id, upload_url, expires_at, next_steps }
        │
        ├─ Route A (default, Cowork): Claude runs
        │     curl -sS -F file=@"<path in uploads folder>" <upload_url>
        │
        └─ Route B (fallback, same chat): Claude calls show_cv_upload_box(upload_id),
              an upload box renders in the chat, user drops the CV, the box POSTs it
              to the same upload_url
        ▼
get_cv_upload(upload_id)  ──►  { status: "received", filename, size }
        ▼
parse_cv / create_candidate_from_cv / attach_cv (upload_id=...)
```

**How a chat picks a route.** The server decides as much as it can and tells the model in the tool result (not the docstring, because FastMCP only forwards text before `Args:`):

- `request_cv_upload` returns ordered `next_steps`: "If the CV is a file in your environment and you can run shell commands, run this curl. If curl fails or you have no shell, call `show_cv_upload_box`."
- The server reads the client's MCP Apps capability from the session. If the client does not advertise MCP Apps, `next_steps` omits Route B and tells the model to report that the file could not be sent and stop. There is no paste-the-text fallback in these tools (owner decision: the existing candidate-from-CV flow already covers parsing; how the tools interact is a follow-up once this works).

### File lifecycle (nothing is kept after it reaches Bullhorn)

- Bytes are held **in memory only**, never written to disk on the server.
- **Deleted immediately** after a successful `attach_file` to Bullhorn, in both `create_candidate_from_cv` and the `attach_cv` commit call. Deletion happens even if later best-effort steps warn.
- **Kept** after `parse_cv` and after the `attach_cv` preview call, because the next call needs the same file.
- **Kept on failure** (Bullhorn error, duplicate found) so the user can retry without re-sending.
- Anything not attached is purged **30 minutes** after upload. Unused tickets expire after 15 minutes.
- `get_cv_upload` reports `attached` (and the Bullhorn file id) once deleted, so the model can tell "done" from "expired".

### New module: `src/bullhorn_mcp/uploads.py`

- `UploadStore`: in-memory dict, thread-safe (`threading.Lock`), keyed by `upload_id`.
  - `create(owner_sub, candidate_id) -> (upload_id, token)`: `upload_id` is a random opaque id; `token` is `secrets.token_urlsafe(32)`, stored only as its SHA-256.
  - `redeem(token, filename, content_type, data)`: atomic single use; rejects unknown, expired (15 min from mint), already-redeemed, oversize, or disallowed extension.
  - `get(upload_id, owner_sub)`: returns the record only to the same Entra `sub` that minted it. Received files live at most **30 minutes** after upload (long enough for `attach_cv`'s preview then commit), then are purged.
  - `mark_attached(upload_id, file_id)`: drops the bytes, keeps a small tombstone (`attached`, Bullhorn file id) until the 30-minute purge.
  - Lazy purge on every call; no background thread.
- Stores the original filename (from `request_cv_upload`), detected format (from extension), size, SHA-256, bytes, `candidate_id` hint.

### `server.py` changes

- **Delete** `_upload_cv_handler`, its `custom_route("/upload-cv")`, the `hmac` import if unused afterwards, and all `UPLOAD_SECRET` handling.
- **Add** `custom_route("/upload/{token}", methods=["POST", "OPTIONS"])`: multipart, field `file`. The token is the only authorisation (not behind Entra, like `/upload-cv` was). Returns JSON `{upload_id, filename, size}` or a 4xx with `{error, message}`. Does **not** call Bullhorn; all Bullhorn writes stay inside MCP tools, where the caller's Entra identity is available. CORS: allow the Claude MCP App sandbox origin (`*.claudemcpcontent.com`) for Route B.
- **New tools** (short descriptions, NFR-8):
  - `request_cv_upload(filename: str, candidate_id: int | None = None)`: `filename` is the name as the user attached it. Mints a ticket for the resolved caller, returns `upload_id`, `upload_url` (`{MCP_BASE_URL}/upload/{token}`), `expires_at`, `next_steps`. Rejects a disallowed extension before any upload.
  - `get_cv_upload(upload_id)`: status `pending | received | attached | expired`, plus filename, size.
  - `show_cv_upload_box(upload_id)`: MCP App UI tool (Route B). Built only if T40.1 passes.
- **Changed tools:** `parse_cv`, `create_candidate_from_cv`, `attach_cv` replace `file_b64` + `filename` + `format` with `upload_id: str`. Filename and format come from the stored upload. `create_candidate_from_cv` keeps its text mode (`content`). Errors: `upload_not_found`, `upload_pending` (ticket minted, no file yet), `upload_expired`, each with a hint naming the next tool to call.

### Route B implementation choice (decided by T40.1)

Preferred: a minimal hand-written MCP App (FastMCP low-level HTML app, one HTML file with a drop zone that `fetch`es `upload_url`, with `connectDomains: ["https://mcp.thepanel.com"]`). It reuses the upload route, so there is one byte path. Fallback option: subclass FastMCP's `FileUpload` provider, which requires adding `fastmcp[apps]` (`prefab-ui`, not installed today) and routes bytes as base64 through an app-only tool call (not model tokens, but a second code path). The CR build picks the first option unless the spike shows the iframe cannot reach our domain.

## PRD amendment (to apply on approval)

- **FR-15 Amendment: CV file intake without base64.** CV files shall reach the server out of band via single-use upload tickets (`request_cv_upload`, `POST /upload/{token}`, `get_cv_upload`). `parse_cv`, `create_candidate_from_cv` and `attach_cv` shall take an `upload_id` instead of base64 content. File bytes shall never be required in a tool argument. The `/upload-cv` endpoint and `UPLOAD_SECRET` are withdrawn. Where the client supports MCP Apps, an in-chat upload box shall be offered as the fallback when the agent cannot send the file itself.
- **NFR-9: Upload ticket security and file retention.** Tickets are single use, expire 15 minutes after issue, are stored only as hashes, are bound to the issuing user, and accept at most 10 MB (Bullhorn's attachment cap) of an allowed CV file type. Received files are held in memory only, readable only by the issuing user, deleted as soon as they are attached in Bullhorn, and purged after 30 minutes otherwise.
- **US-48: Attach a CV once in Cowork.** As a consultant, I attach a CV to a Cowork chat and ask Claude to add the candidate (or attach it to an existing one), and the file is parsed and attached in Bullhorn without me selecting it again.
  Acceptance: Claude calls `request_cv_upload`, sends the attached file with curl, and completes `create_candidate_from_cv` or `attach_cv` with the `upload_id`. No base64 appears in the conversation.
- **US-49: Upload box fallback in the same chat.** As a consultant, if Claude cannot send the file itself, an upload box appears in the chat, I drop the CV there, and Claude carries on.
  Acceptance: on curl failure, Claude calls `show_cv_upload_box`, the dropped file is received against the same ticket, and the flow completes. US-31 acceptance text is updated from "base64-encoded file" to "uploaded file (`upload_id`)".

## Risks

- **Cowork egress:** if neither the allowlist nor "All domains" lets a POST through, Route A fails and everything rests on Route B. T40.1 surfaces this before any build.
- **MCP Apps in Cowork:** unverified. If unsupported, there is no in-chat fallback and a failed curl just reports the failure. T40.1 decides, and the owner is consulted before building without Route B.
- **Security of an unauthenticated route:** mitigated by 256-bit single-use tokens, 15-minute expiry, hashed storage, size and type limits, and owner-bound retrieval. The route never writes to Bullhorn.
- **Restart during a handoff** drops the upload. Acceptable; the user re-runs the step.
- **"All domains" egress** broadens what every Cowork session can reach. That is an org security decision for the owner, only needed if the allowlist fails.
