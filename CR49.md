# CR49: Job start date defaults to today and is stored the way the Bullhorn UI stores it

## Status: APPROVED (owner, 2026-11-20). Raised by the owner 2026-11-20. Sprint 45, v0.0.60. PRD amendment applied to PRD.md 2026-11-20 (pushed in 5c964d5). Planned as Sprint 45 at the 2026-11-20 replan (IMPLEMENTATION-PLAN.md, T45.1 to T45.7).

**Owner answers (2026-11-20):** Q1: an explicitly empty start date on `update_job` defaults to today, the same as on create; an update that does not mention the start date leaves the existing date alone. Q2: fixed values (named constants) for now. Q3: add `tzdata`. Q4: PRD text approved as written (FR-13 Amendment bullet 3 gained one sentence recording Q1).

## Motivation

The company has decided a new job's start date defaults to today unless a date is stated. Investigating that (2026-11-20, read-only checks plus one approved test job) found a second, related bug.

**How Bullhorn stores a start date.** `JobOrder.startDate` is a date-only field (`/meta`: `dataType: Timestamp`, `dataSpecialization: DATE`, not required). The Bullhorn UI stores the picked date as **midnight America/New_York** on that date: 04:00 UTC in summer (EDT), 05:00 UTC in winter (EST). The date is the consultant's local (Irish) date, not New York's: job 51476 was created at 00:36 Irish time on 15 Oct (still 14 Oct in New York) and its start date is 15 Oct. All 500 most recent jobs have a start date. Consultants' `CorporateUser.timeZoneOffsetEST` is 300 (UK); API users are 0.

**The bug.** Four of those 500 jobs had their start date sent through the MCP: 51533, 51489, 51459 and 51437 (the live test job). Each holds **midnight UTC**, because Claude converted the stated date itself. The owner checked the UI: 51533 (meant 20 Nov) shows **19/11**, 51489 (meant 1 Feb 2027) shows **31/1**. Midnight UTC is 19:00 or 20:00 the evening before in New York, so the UI shows the day before.

**What Bullhorn does with no start date.** Test job 51534 was created through the API without `startDate` (owner approved; soft-deleted afterwards). Bullhorn filled in 2026-11-20 05:00 UTC, midnight New York today, and the UI showed 20/11. Bullhorn uses the New York date, so a job created between 00:00 and 05:00 Irish time (04:00 in summer) would get yesterday. The UI uses the consultant's date.

**Where the question comes from.** The MCP does not ask for a start date. The Cowork `new-job-setup` skill does ("Always ask"). The owner is changing the skill separately in Cowork (see Rollout).

**Owner goal (2026-11-20):** the MCP behaves as if the job had been entered through the UI. A job with no stated date looks exactly as if the consultant had picked today in the UI. It is never left blank and never relies on Bullhorn's own fallback.

## Goals

- `create_job` with no start date sends today's Irish date, stored as midnight New York.
- `create_job` and `update_job` store a stated start date as midnight New York on that date, so the UI shows the date that was meant.
- Claude can pass the date as plain `"YYYY-MM-DD"` and never does the time-zone arithmetic itself.

## Non-goals

- **Other date fields** (`dateEnd`, Placement dates, Candidate `dateAvailable`, and so on). Owner scoped this CR to `JobOrder.startDate` only (2026-11-20). They likely share the bug when written through the MCP; that is a later CR.
- **`_iso_to_epoch_ms()`** (`server.py:336`) is unchanged. `list_placements` uses it for UTC-midnight filter bounds, which is a different job.
- **Fixing the three affected jobs** (51533, 51489, 51459). Owner chose not to (2026-11-20).
- **The Cowork skill text.** It lives outside this repo; the owner edits it in Cowork.
- CV work-history dates. The parser stores them at noon New York (16:00/17:00 UTC), which displays correctly.

**New: FR-13 Amendment: Job Start Date (CR49)**, inserted after FR-13:

> - `create_job` shall set the JobOrder start date to today's date when none is given, so a job is never created without one. "Today" is the date in the consultants' time zone (Ireland), not the server's or Bullhorn's.

## Design

### `src/bullhorn_mcp/server.py`

1. **Constants:**
   - `_BULLHORN_DATE_TZ = ZoneInfo("America/New_York")`: Bullhorn's storage zone for date-only fields.
   - `_CONSULTANT_TZ = ZoneInfo("Europe/Dublin")`: the zone that defines "today" and reads timestamps. Fixed constants (owner, Q2); an env var only if the server goes multi-tenant.

2. **New helper `_job_start_date_ms(value, *, now=None) -> int`.** Returns epoch ms for midnight New York on the intended calendar date. Raises `ValueError` on bad input.
   - **`None` or `""`:** today's date in `_CONSULTANT_TZ` (from `now`, injectable for tests, default `datetime.now(timezone.utc)`).
   - **`str` matching `YYYY-MM-DD` exactly:** that date. Any other string (an ISO datetime, `"ASAP"`, `"next Monday"`) raises.
   - **`int` or `float` (not `bool`):** treated as epoch ms. The date is the **calendar day in Europe/Dublin**, then re-encoded.
   - **Anything else** (`bool`, dict, list): raises.
   - Then `datetime(y, m, d, tzinfo=_BULLHORN_DATE_TZ)` converted to epoch ms.

   **Why the Dublin day for timestamps** (this corrects what was said in discussion on 2026-11-20, where the UTC day was suggested). Reading the timestamp in Dublin gives the intended date for every encoding seen or likely:
   - midnight UTC (the 4 bad jobs);
   - midnight New York (the UI's 04:00/05:00 UTC);
   - noon New York (the CV parser);
   - midnight Irish time (23:00 UTC the day before in summer).

   The UTC day gets the last case wrong. The rule is idempotent: a correct value comes back unchanged. That makes a read-then-write-back through `update_job` safe, including in the late-October and late-March weeks when only one of the two zones has changed clocks (jobs 51497-51503 sit at 04:00 UTC while Dublin is already on GMT).

3. **`create_job`:** after `merged = {**resolved_defaults, **resolved_caller}` (`server.py:1777`), set `merged["startDate"] = _job_start_date_ms(merged.get("startDate"))`. It runs on the resolved, merged dict, so `"Start Date"`, `"startDate"` and any alias are all caught. Precedence: caller value, then `BULLHORN_JOBORDER_DEFAULTS`, then today. It runs **before** the `BULLHORN_JOBORDER_REQUIRED` check, so a configured `startDate` requirement is always met. On `ValueError`, it returns `{"error": "invalid_start_date", "message": ..., "hint": "Pass the date as YYYY-MM-DD, or leave it out for today."}` with no API call.

4. **`update_job`:** after `resolve_fields`, it acts only if `"startDate"` is in the resolved dict. If so, it is normalised with the helper, with the same error shape. An explicit `None` or `""` becomes today, the same as on create (owner, Q1). **If the update does not mention the start date, the field is not sent, so the job's existing date is left alone.**

5. **Docstrings (the interface, NFR-8):** one short sentence in the `fields` Args entry of both tools, for example: *"startDate: pass "YYYY-MM-DD"; create_job uses today when it is left out."* FastMCP keeps Args entries as the parameter description, so Claude sees it. Check the token cost with `scripts/measure_descriptions.py`.

### Other JobOrder write paths (checked 2026-11-20)

`client.create("JobOrder", ...)` and `client.update("JobOrder", ...)` are called only in `create_job` (`server.py:1798`) and `update_job` (`server.py:1825`). `update_record` accepts ClientContact, ClientCorporation and Candidate only, and `bulk_import` writes companies and contacts only. Nothing else needs changing.

### Dependencies

`zoneinfo` is in the standard library and needs the system tz database (present locally at `/usr/share/zoneinfo`). No module in `src/` uses it yet. Options: add `tzdata` to `pyproject.toml` dependencies (works anywhere, small), or rely on the box's `/usr/share/zoneinfo`. **Decided (owner, Q3): add `tzdata`** to `pyproject.toml` dependencies, so a missing system database cannot break `create_job` at import time.
