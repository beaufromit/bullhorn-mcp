# CR48: Consultant chooses each overwrite on attach_cv

## Status: APPROVED (owner, 2026-11-13). Raised by the owner during the Sprint 43 build; built in Sprint 43 as T43.16 (v0.0.58), before the review.

**Owner answers (2026-11-13):** Q1 (a), replace `confirm` with `overwrite`. Q2: not sure; no caller in this repo, and the Panel skills seen do not do CV uploads, so the risk is low; at the v0.0.58 deploy the owner searches Cowork skills and saved prompts for `confirm=True` on `attach_cv`. Q3: PRD text approved as written. Additions stay automatic (owner confirmed the two-group split).

## Motivation

`attach_cv` adds what the CV has that the record lacks straight away, and returns every field that already holds a different value in `pending_overwrites`. Today the only way to apply them is `confirm=True`, which writes **all** of them. A consultant who says "yes to the job title, no to the company, keep the old description" cannot be served: Claude can only write all or nothing.

The code could almost do it already (`fields_to_update` limits which fields are considered), but:

- `fields_to_update` is described only under `Args:`, which FastMCP drops, so Claude never sees it (see the FastMCP docstring note in the project memory and CR34).
- The response hint says "call attach_cv again with the **same arguments** and confirm=True", which steers Claude to all or nothing.
- `fields_to_update` means "fields to consider", not "fields the consultant approved". Using it for both is easy to get wrong.

Seen live in T43.13 (2026-11-13, Candidate 173063): `description` came back as a pending overwrite (4,557 vs 5,028 chars) next to whatever else differed, and the only way forward was all or nothing.

## Where the choice lives

The MCP cannot show a prompt itself. The consultant chooses in the chat; Claude asks because the tool text and the response hint tell it to. The guarantee stays in code: nothing is overwritten unless the call names it. This CR makes the consultant's per-field choice something Claude must pass explicitly, so a field the consultant did not approve cannot be written by accident.

## PRD trace (amendment needed, proposed text)

FR-15 Amendment 2, bullet 4, currently: "Updating an existing Candidate from a CV shall apply additions (...) immediately, and shall replace an existing value only on an explicit confirmation, which a caller with no consultant present may give up front."

Proposed: "Updating an existing Candidate from a CV shall apply additions (the file, new work history, education and skills, empty fields) immediately, and shall replace an existing value only when the caller names that field as confirmed. The consultant accepts or rejects each proposed overwrite separately; a rejected field is left as it is and reported as kept. A caller with no consultant present may confirm every overwrite up front." (CR48)

US-50 acceptance, currently "...Claude shows any value that would be replaced and replaces it only after the consultant confirms." Proposed: "...Claude shows each value that would be replaced, with the current and proposed value, and replaces only the ones the consultant accepts; the others are left as they are."

## Design

### D1. How the choice is passed (owner decision, Q1)

Recommended **(a)**: replace `confirm: bool` with `overwrite: list | None`.

- Omitted or empty: as today without confirm. Additions are written, differing fields come back in `pending_overwrites`, nothing is overwritten.
- A list of field names (API names or display labels, resolved as `fields_override` keys are): only those pending overwrites are written. Every other pending overwrite is left as it is and listed under `kept`.
- `["all"]`: every pending overwrite is written. This is the automation path (no consultant present), and the tool text says to use it only then.
- A name in `overwrite` that is not a pending overwrite (equal value, empty on the record, not in the parse) is ignored with a warning naming it.

(b) Keep `confirm` and add `overwrite`: `confirm=True` alone still writes all of them. Smaller change, but Claude keeps a one-flag way to write everything in a consultant flow, which is what this CR is closing.

(c) No new parameter: document `fields_to_update` on the confirm call and change the hint. Cheapest, but it mixes "consider" with "approved" (see Motivation).

### D2. Response

- Without `overwrite`: unchanged (`pending_overwrites` plus `hint`). The hint and the tool description say: show the consultant each pending overwrite as current value vs proposed value (for `description`, the two lengths), ask them to accept or reject each one, then call `attach_cv` again with the same arguments plus `overwrite=[accepted fields]`. If they reject all of them, do not call again.
- With `overwrite`: `overwritten` (the fields written, as today) and new `kept` (the pending overwrites the consultant did not accept, each with its current value, so Claude can say what was left alone). Nothing added on the first call is added twice (unchanged behaviour).

### D3. Unchanged

Additions are written on every call, as today. `fields_to_update` keeps its meaning (which fields are considered at all). The file-only path for a Candidate the upload created is unchanged. `create_candidate_from_cv` has no overwrites and is not touched. Outcome logging is unchanged.
