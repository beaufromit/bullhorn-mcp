## Part 1 — What this adds and why it isn't the default Perplexity connector

The Panel-layer Perplexity connector exposes `perplexity_search`, `perplexity_ask`,
`perplexity_research`, `perplexity_reason`. Verified against the live connector
schema: **none of them accept a `search_type` parameter**, so none can reach
Perplexity's people index. `perplexity_search` is general web search only.

Perplexity's people index is a distinct mode of the same Search API, activated by
`search_type: "people"`. It returns individual-profile results (predominantly
LinkedIn) rather than curated web pages. This CR exposes exactly that mode as one
MCP tool, so any client of this server can source candidates that are not yet in
Bullhorn.

This is the first non-Bullhorn outbound dependency in the server. It is kept fully
isolated from the Bullhorn client and auth (own module, own error type) so a
Perplexity outage or missing key can never affect Bullhorn tools, and vice versa.

## Part 2 — Design

### New module: `src/bullhorn_mcp/perplexity.py`

A thin, self-contained HTTP wrapper. No dependency on `BullhornClient`,
`BullhornAuth`, or `BullhornConfig`.

```python
PERPLEXITY_SEARCH_URL = "https://api.perplexity.ai/search"

class PerplexityError(Exception):
    """Raised on missing key, non-200, or transport failure."""

def search_people(
    api_key: str,
    queries: list[str],
    max_results: int = 10,
    timeout: float = 30.0,
) -> list[dict]:
    """POST /search with search_type='people'. Returns the raw `results` list.
    Raises PerplexityError with a clean message on any failure."""
```

- Request body: `{"query": queries, "search_type": "people", "max_results": max_results}`.
  The API accepts `query` as a list; we always send the list.
- Auth: `Authorization: Bearer <api_key>`. The key is never logged and never put
  in the returned payload or any exception message.
- Non-200: parse `{"error": {"message", "type", "code"}}` and raise
  `PerplexityError(f"{type}: {message}")`. Transport errors (`httpx.HTTPError`)
  are wrapped in `PerplexityError` too.
- Uses `with httpx.Client(timeout=...) as client:` — same idiom as `client.py`.

### New tool: `people_search_perplexity` in `server.py`

```python
@mcp.tool()
def people_search_perplexity(
    queries: list[str],
    max_results: int = 10,
) -> str:
```

- **Docstring**: the verbatim Perplexity people-search description (see Part 3),
  placed **before** `Args:` so FastMCP does not drop it. (Project fact: FastMCP
  only surfaces docstring text before `Args:`.)
- **Validation (before any HTTP call):**
  - `queries` empty → error JSON `{"error": "queries_required", ...}`.
  - `len(queries) > 5` → error JSON `{"error": "too_many_queries", ...}`.
  - any blank/whitespace-only entry → error JSON.
  - `max_results` clamped to 1..50, default 10. The live API returns up to 50
    in one call and **does not paginate** (verified: `offset` and `page` are
    silently ignored and every call starts from the same top result). "Find me
    more" is therefore served by re-calling with a higher `max_results`, or by
    varying/refining the query, not by paging. The docstring says so.
- **Missing key**: if `os.getenv("PERPLEXITY_API_KEY")` is falsy, return a clean
  error JSON `{"error": "perplexity_key_not_configured", ...}`. Never raise at
  import time and never crash the tool.
- **Call** `perplexity.search_people(...)`; on `PerplexityError` return
  `{"error": "perplexity_error", "message": str(e)}`.
- **Format** compactly for the model via `format_response`:

```json
{
  "queries": ["..."],
  "count": 3,
  "note": "Results are a single merged, ranked list across all queries, capped at max_results total. Source: Perplexity people index (external, not Bullhorn).",
  "results": [
    {"title": "...", "url": "...", "snippet": "<truncated>", "last_updated": "2026-09-11", "date": "2025-07-17"}
  ]
}
```

  - `snippet` truncated to ~300 chars with an ellipsis when longer.
  - `date` included only when the API returns it (people mode usually omits it).
  - The `note` makes the merge/cap behaviour and the external source explicit to
    the model, since array queries have no per-query grouping.

### Config

- `PERPLEXITY_API_KEY` is **not** added to `BullhornConfig` (it is not a Bullhorn
  credential). It is read directly via `os.getenv` in the tool. This keeps the
  Bullhorn config surface unchanged.
- Add a commented placeholder to `.env.example`:
  `# PERPLEXITY_API_KEY=  # required only for people_search_perplexity (external candidate sourcing)`

### Read-only guarantee

The tool makes zero Bullhorn calls and no writes anywhere. It only POSTs a search
query to Perplexity.

## Part 3 — Tool description (verbatim, pulled live from the docs)

Verbatim from `https://docs.perplexity.ai/docs/search/filters/people-search`:

> "Searches a dedicated index for individual profiles and employee data. Returns
> information including names, job titles, companies, and profile URLs. Use this
> tool ONLY when the user specifically wants individual employee lookups, career
> history, or people who match work-related criteria (e.g., listing employees at a
> company by location). For general questions about executives, leadership teams,
> or public figures, prefer search_web instead as it returns richer curated
> results."

**D1 — RESOLVED (owner, 2026-09-23).** Keep the verbatim opening (through
"...listing employees at a company by location).") and replace only the final
steer sentence. Two reasons, both evidence-backed by the live benchmarks in the
appendix: (1) `search_web` is not a tool in this MCP, and (2) the recruiter's
dominant job is sourcing/mapping, where this tool wins decisively, so the
original "prefer search_web" steer would misroute. Crucially the replacement must
**not exclude this tool** for the single-person case: people mode returned the
correct acting CFO at rank 1 for "CFO of Ryanair," it is just noisy after that.

Final description text (this is what ships, placed before `Args:`):

> "Searches a dedicated index for individual profiles and employee data. Returns
> information including names, job titles, companies, and profile URLs. Use this
> tool ONLY when the user specifically wants individual employee lookups, career
> history, or people who match work-related criteria (e.g., listing employees at
> a company by location). This tool is strongest for sourcing or mapping multiple
> people who match criteria: population-shaped queries (role plus location or
> sector) return many precise matches. For a single specific named individual or
> a company's specific office-holder, prefer a general web search first and fall
> back to this tool if the results are unsatisfactory. Results are a snapshot and
> may not reflect a person's current role."

Everything before the "This tool is strongest..." sentence is verbatim Perplexity
wording; the rest is the replacement steer.

### The market-map fan-out is NOT built here

For wide market maps, coverage comes from issuing several population-shaped
queries (sub-role, location slice, seniority band) and merging/deduping, plus
cross-referencing Bullhorn. That is model/orchestration judgement and belongs in
a separate **market-map skill** that drives this tool as a primitive. It is being
specced in a separate session and is out of scope for CR38. This CR ships only
the raw primitive.

## Part 4 — Tests (`tests/test_server.py` + `tests/test_perplexity.py`)

respx-mocked, matching the repo's existing style. No live calls in tests.

`tests/test_perplexity.py` (module-level):
- happy path single query → returns parsed `results` list; asserts request body is
  `{"query": [...], "search_type": "people", "max_results": ...}` and the
  `Authorization` header carries the bearer key.
- 401 error body → raises `PerplexityError` with the API message; key not leaked.
- 400 validation body → raises `PerplexityError`.
- transport error → wrapped in `PerplexityError`.

`tests/test_server.py` (tool-level, `TestPeopleSearchPerplexity`):
- happy path → formatted JSON with `count`, `results`, `note`; snippet truncated.
- array of 5 queries → accepted; request body `query` is the 5-item list.
- empty `queries` → error JSON, **no HTTP call made** (assert respx route not hit).
- 6 queries → `too_many_queries` error, no HTTP call.
- blank entry → error, no HTTP call.
- `PERPLEXITY_API_KEY` unset (monkeypatch) → `perplexity_key_not_configured`
  error, no HTTP call.
- upstream 401 → `perplexity_error` surfaced cleanly; key absent from output.
- `max_results` clamping (0 → 1, 100 → 50).

## Scope boundaries

- **No orchestration or automation is built here.** This MCP is a passive tool
  provider with no automation mechanism. Any Bullhorn-first-then-external flow,
  or logic for deciding when to reach outside Bullhorn, belongs in a Claude
  **skill** (the same shape `panel-candidate-search` already uses), where it can
  be tuned without a server redeploy and does not grow the tool surface against
  the CR35 consolidation goal. This CR delivers the raw tool only.
- No changes to any other open issue in the repo (`bha-expired-list-ids.md` work
  etc.).
- No new dependency added to `pyproject.toml` — `httpx` and `python-dotenv` are
  already present.

## Risks

- **R1 — external dependency in a Bullhorn server.** Mitigated by full isolation:
  own module, own error type, no shared client/auth, clean per-call failure.
- **R2 — Perplexity API drift.** The `search_type: "people"` mode and response
  fields are verified today (Evidence appendix) but are an external contract that
  could change. Formatting tolerates a missing `date` and unknown extra keys.
- **R3 — description referencing `search_web`** (see D1). Resolved by decision.
- **R4 — token cost of the verbatim description** in the startup tool-list. It is
  ~90 words, one tool, additive. Acceptable; can be measured with
  `scripts/measure_descriptions.py` if wanted.

## Evidence appendix (live, read-only, 2026-09-22)

All via `.venv/bin/python` against the live Search API with the `.env` key.

- `POST /search` `{"query":"Jane Smith financial controller Dublin","search_type":"people","max_results":3}`
  → `200`, 3 LinkedIn-profile results. Each result keys:
  `["last_updated","snippet","title","url"]` (no `date`).
- Plain search (no `search_type`) on the same query → `200`, mixed results
  (LinkedIn, TheOrg, job ads); some results carried `date`. Confirms people mode
  is materially different.
- Array query `["Mary Kelly ...","Tom Byrne ..."]`, `max_results:3` → `200`,
  **3 results total, merged/ranked**, no per-query attribution field.
- Invalid key → `401` `{"error":{"message":"Invalid API key provided...","type":"invalid_api_key","code":401}}`.
- Empty query → `400` `{"error":{"message":"query validation: query 1 length must be between 1 and 8192 characters, got 0","type":"invalid_request","code":400}}`.
- Verbatim tool description pulled from the people-search docs page (Part 3).

### People vs web benchmark, and people-mode precision (2026-09-23)

Distinct individuals (proxy: unique `linkedin.com/in/` URLs) returned per mode,
`max_results` 20:

| Query | People mode | Web mode |
|---|---|---|
| "CFO of Ryanair" (single-entity) | 20 (1 right, rest decaying noise) | 2 + curated leadership pages naming the actual Group CFO |
| "finance team at Kerry Group" (company map) | 20 real individuals | 8 profiles + TheOrg org chart |
| "financial controller Dublin" (market map) | 20 real individuals | **0 people, all job ads** |
| "FP&A analyst Cork" (niche) | 20 real individuals | 6 profiles + salary/job pages |

Precision test, people mode, `max_results` 50, "financial controller Dublin":
**50/50 results were named Financial Controllers in Dublin, no tail decay
(first-10 and last-10 both 10/10), 50 unique URLs, no duplicates.** A genuine
one-shot market map.

Single-entity precision test, people mode, "CFO of Ryanair": rank 1 was the
correct acting CFO; ranks 2-20 decayed into Ryanair-adjacent finance staff,
executive assistants, a sales executive, an Aer Lingus COO, and CFOs of unrelated
firms. Confirms the tool pads to the cap and is a poor single-entity instrument.

**Rule this establishes:** precision is governed by query shape, not the tool.
Population-shaped queries (role + location/sector) yield high precision up to the
cap; single-entity queries ("who is THE X of company Y") return the top hit plus
padding. This is the basis for the D1 wording and for placing fan-out/market-map
in a skill.
