# CR40: add_note must set personReference for non-person targets

## Status: APPROVED (owner, 2026-09-23). PRD amended (FR-7 Amendment 2, FR-16 Amendment, US-46, US-47). Sequenced as Sprint 39 after CR38 (v0.0.51). Replanned 2026-09-23 (IMPLEMENTATION-PLAN.md Sprint 39). Next: build.

## Motivation

On 22-23 Sep 2026, `add_note(entity="JobOrder", entity_id=51437, action="Claude note", comments="test")` failed with:

```
400 {"errorMessage":"error persisting an entity of type: Note",
     "errorMessageKey":"errors.cannotPersistEntity",
     "errors":[{"detailMessage":"missing required property: personReference",
                "propertyName":"personReference","type":"MISSING_REQUIRED_PROPERTY"}],
     "entityName":"Note"}
```

The same call against ClientContact 145635 works (note 2653704). Bullhorn requires every Note to carry a `personReference`, but `client.add_note` (`_ENTITY_FIELD`) only sets it when the target is itself a Candidate or ClientContact. The JobOrder, ClientCorporation, Placement, Lead and Opportunity targets have never been able to write a note.

## Live evidence (read-only, 2026-09-23)

1. **`/meta/Note` (meta=full) does not mark `personReference` as required.** The requirement is enforced only server-side at persist time, so the /meta `required` flag cannot be used to detect it.
2. **`/meta/Note` has no `clientCorporation` field.** The note-link fields it does have are the TO_ONEs `personReference` (Person), `commentingPerson` (Person) and `jobOrder`, and the TO_MANYs `jobOrders`, `placements`, `leads`, `opportunities`, `candidates`, `clientContacts`, `corporateUsers`, `people` and `entities` (NoteEntity). The current ClientCorporation branch sends `clientCorporation: {id}`, which is not a Note field, so company notes are broken twice over.
3. **Notes created in the Bullhorn UI against a job leave the `jobOrder` TO_ONE null.** They link the job through the `jobOrders` TO_MANY, backed by NoteEntity rows. Three real jobs show this (read-only):
   - Note 2652133 on job 51339: `personReference` = ClientContact 163296, `jobOrder: null`, `jobOrders` = [51339], NoteEntity rows `JobOrder/51339` and `User/163296`.
   - Note 2652413 on job 51345: `personReference` = Candidate 172083, `jobOrder: null`, `jobOrders` = [51345], NoteEntity rows `Placement/11681`, `JobOrder/51345` and `User/172083`.
   - Note 2650741 on job 51337: same shape as 2652413 (`JobOrder`, `Placement` and `User` rows).
4. **On ClientCorporation, `notes` is a SCALAR text field and not an association.** As a result `GET /entity/ClientCorporation/10666/notes` returns 500 `{"errorMessage":"Unknown entity: String"}`, so `get_notes_for_entity("ClientCorporation", ...)` is broken today, separately from this bug. The note association on the company is **`clientContactNotes`** (TO_MANY Note). For 10666 it already returns notes whose `personReference` is one of the company's contacts, including 2653704 (Duke Nukem, 145635).
5. **Test records:** JobOrder 51437 has `clientContact` 145635 (Duke Nukem) and `clientCorporation` 10666 (Beaus Test Company, Active). Company 10666 has 19 non-deleted contacts, so "first active contact" is an arbitrary pick. Job 51437 currently has no notes.
6. **No JobOrder on this tenant lacks a clientContact** (Lucene `-clientContact.id:[0 TO 999999999]` gives total 0). The no-person fallback cannot be tested against a real record.
7. Lead has `personSubtype`, so it is a Person subtype. Opportunity and Placement both have `clientContact`, and Placement also has `candidate`.

## Is a "ClientCorporation note" a real thing? (read-only, 2026-09-23)

No, it isn't. Across 80 real notes returned by `clientContactNotes` for companies 10550 (Writech Group) and 10666, **zero** NoteEntity rows target `ClientCorporation`. Every row targets `User` (the contact), plus the occasional `JobOrder` or `Opportunity`. Here is what makes up "company notes" in Bullhorn:
- the company's Notes tab, which is `clientContactNotes`: the notes on its contacts;
- the scalar `ClientCorporation.notes` field, labelled "Company Comments", which is part of the record (writable through `update_record`).

The `ClientCorporation` branch of `add_note` is therefore itself the bug. It sends `clientCorporation`, which is not a Note field, so it has never been able to work. `/query/NoteEntity` returns total 0 even for `targetEntityName='JobOrder'`, although such rows exist (14725325), so it cannot be used to prove that something is absent.

## Goals

1. `add_note` succeeds for every entity it advertises, and each note has a valid `personReference`. ClientCorporation is no longer advertised: a company note is a note on one of its contacts.
2. The note appears under `get_notes_for_entity` for the target record (acceptance tests 1 to 3 in the bug report).
3. ClientContact and Candidate notes behave exactly as they do today (payload unchanged).
4. When no person can be resolved, the tool uses a verified fallback or returns a clear `no_linked_person` error, never the raw 400.

## Non-goals

- No manual NoteEntity creation. U1 showed that the TO_MANY in the create body produces the link.
- No change to `search_notes` Lucene behaviour (`/search/Note` still returns nothing on this tenant).
- No backfill of the job link for existing notes.

## Design

### Person resolution per target (client.py)

Owner decisions (2026-09-23):
- Notes on non-person records attach to the **consultant**, meaning the logged-in user, and **not** to the record's contact or candidate. Otherwise every job note would pile up on the client contact's timeline.
- The rule is the same for JobOrder, Placement and Opportunity.

| Target | personReference | Record link on the Note |
|---|---|---|
| Candidate, ClientContact | the record itself (unchanged) | none (unchanged) |
| Lead | the record itself (verified by U3, note 2653733) | `leads: [{id}]` (the payload U3 verified) |
| JobOrder | the logged-in CorporateUser (`resolve_caller`, already used for `commentingPerson`) | `jobOrders: [{id}]` (as the UI does), not the `jobOrder` TO_ONE |
| Placement | the logged-in CorporateUser | `placements: [{id}]` |
| Opportunity | the logged-in CorporateUser | `opportunities: [{id}]` |
| ClientCorporation | **removed as an add_note target** (owner decision 2026-09-23). Returns `{"error":"company_notes_live_on_contacts", ...}` listing the company's active contacts, and points to `update_record` for "Company Comments" | n/a |

This is exactly the payload probe P2 verified (note 2653714): `personReference` = `commentingPerson` = CorporateUser 142235, plus `jobOrders` [51437]. It shows on the job, and on no contact or candidate.

**Fallback when the caller identity cannot be resolved** (`IdentityResolutionError`, for example stdio mode with no Entra token): use the record's `owner` (one `GET {Entity}/{id}?fields=owner(id)`; JobOrder, Placement and Opportunity all have `owner` → CorporateUser in /meta). If that is also empty, return `{"error": "no_linked_person", "message": ...}` and do not attempt the PUT. The raw 400 never surfaces.

A new optional `person_id: int | None` argument on the `add_note` tool overrides this for JobOrder, Placement and Opportunity. The agent can use it when the user explicitly wants the note on a specific person's timeline too, for example the candidate they just called about the job. It is ignored for Candidate, ClientContact and Lead.

Record links go in the create body (verified by U1). The `ATTEMPT_TO_SET_TO_MANY` warning is expected and is ignored.

### get_notes_for_entity (server.py)

For `entity == "ClientCorporation"`, read the `clientContactNotes` association instead of `notes`. This fixes the 500 described in evidence item 4. Every other entity is unchanged.

**search_notes (replan 2026-09-23, owner decision):** confirmed that the `search_notes` entity_filter path makes the same `notes` association call (`server.py:3368`), so it also 500s on companies. It gets the same fix, through one shared helper that picks the association name. The FR-16 Amendment and US-47 were extended to cover it.

### Docstrings

- The `add_note` tool docstring states which person each entity's note is attached to (the record itself for Candidate, ClientContact and Lead; the logged-in consultant for JobOrder, Placement and Opportunity). It documents `person_id`, and says that company notes belong on a contact.
- The Returns and Examples sections are dropped by FastMCP, so this goes in the text before `Args:`.
- The stale ClientCorporation mention is removed.

## PRD amendment (approved and applied to PRD.md, 2026-09-23)

### 1. FR-7 Amendment 2: Every Note has a person (insert after the existing FR-7 Amendment, PRD.md line 175)

```markdown
### FR-7 Amendment 2: Add Notes, Person Reference and Supported Targets

Bullhorn rejects any Note without a `personReference` (a Person: Candidate, ClientContact, Lead or CorporateUser) with `400 missing required property: personReference`. The `/meta/Note` required flag does not show this; it is enforced at persist time. The `add_note` tool shall therefore always send a `personReference`, as follows:

- **Candidate, ClientContact, Lead**: the record itself. The Candidate and ClientContact payloads are unchanged from FR-7.
- **JobOrder, Placement, Opportunity**: the logged-in consultant (the same CorporateUser stamped as `commentingPerson`). The note is linked to the record through the matching TO_MANY field (`jobOrders`, `placements`, `opportunities`) in the create body, so it appears in that record's notes. It is never attached to the record's client contact or candidate implicitly, so job notes do not accumulate on a contact's timeline.
- If the caller's identity cannot be resolved, the record's `owner` is used instead. If there is no owner either, the tool returns a `no_linked_person` error and writes nothing.
- An optional `person_id` argument lets the caller attach a JobOrder, Placement or Opportunity note to a specific person instead of the consultant.
- **ClientCorporation is not a note target.** Bullhorn has no company-level Note; the Note entity has no company field, and the notes shown on a company are the notes of its contacts. `add_note` on a ClientCorporation shall return a `company_notes_live_on_contacts` error that lists the company's active contacts, write nothing, and point to `update_record` for the company's "Company Comments" field.
- Bullhorn's `ATTEMPT_TO_SET_TO_MANY` warning in the create response is expected and shall not be treated as a failure.
```

### 2. FR-16 amendment: Company notes read path (insert after FR-16)

```markdown
### FR-16 Amendment: Company Notes

On ClientCorporation, `notes` is a text field ("Company Comments"), not a note association, so `GET /entity/ClientCorporation/{id}/notes` fails with a 500. `get_notes_for_entity(entity="ClientCorporation", ...)` shall read the `clientContactNotes` association instead, returning the notes of the company's contacts in the standard pagination envelope (FR-19). The `search_notes` `entity_filter` path shall use the same association when the filter type is ClientCorporation. All other entities keep the `/notes` association.
```

### 3. User stories (insert after US-45)

```markdown
**US-46: Add a note to a job, placement or opportunity**
As a consultant, I want to add a note to a job, placement or opportunity and see it on that record, attributed to me, so that the record's history is complete without the note also landing on the client contact's or candidate's timeline.
- **Acceptance**: `add_note(entity="JobOrder", entity_id=51437, action="Claude note", comments="...")` succeeds, and `get_notes_for_entity("JobOrder", 51437)` returns the note with `personReference` set to the logged-in consultant. The note does not appear in `get_notes_for_entity("ClientContact", 145635)` (the job's contact). The same holds for Placement and Opportunity. Passing `person_id` attaches the note to that person instead. When neither the caller nor the record owner can be resolved, the tool returns a `no_linked_person` error and writes nothing, never the raw Bullhorn 400.

**US-47: Company notes go to a contact**
As a consultant, I want a clear redirect when I try to add a note to a company, and I want to be able to read a company's notes, so that notes land on the right person and I can see the company's history.
- **Acceptance**: `add_note(entity="ClientCorporation", entity_id=10666, ...)` returns `company_notes_live_on_contacts` with the company's active contacts and makes no write. `get_notes_for_entity("ClientCorporation", 10666)` returns the notes of the company's contacts (no 500), and `search_notes(query, entity_filter={"type": "ClientCorporation", "id": 10666})` searches those same notes (no 500). Candidate, ClientContact and Lead notes behave as before.
```
