# CR42: Fix Bullhorn resume parser parameters (CV parsing fails on every path)

## Status: APPROVED (2026-09-29). Owner chose HTML for the Candidate description. Assumptions A1 to A4 accepted. PRD amended (FR-15, US-31). Replanned as Sprint 40B, built (58fbf1d), T40B.3 live smoke passed. Next: review, tag v0.0.53, deploy, re-run T40.8.

## Motivation

The T40.8 live acceptance run for CR41 (v0.0.52, deployed 2026-09-29) showed CV upload tickets working end to end (ticket, curl upload, `get_cv_upload` = `received`), but every parse failed with Bullhorn 400s, so no candidate could be created from a CV:

- `parse_cv`, `create_candidate_from_cv(upload_id=...)`, `attach_cv`: `400 "Invalid format: Must be 'text' or 'html'."`
- `parse_cv_text`, `create_candidate_from_cv(content=...)`: `400 "Missing parameter format."`

This is not a CR41 regression. `client.parse_resume_file` and `client.parse_resume_text` are unchanged since CR19 (a5cc149); parsing has never worked on this tenant. `tests/test_client.py` pins the wrong value (`assert "populateDescription=true" in url`), which is why the suite never caught it (the review loop's documented live-API blind spot).

## Live evidence (parse only, nothing written, owner-approved, 2026-09-29)

Fixtures `tests/fixtures/sample_cv/cr41_test_candidate.{docx,pdf}`, called through `BullhornClient._request_multipart` / `_request`:

| Call | Result |
|---|---|
| `POST /resume/parseToCandidate`, `format=docx`/`pdf`, `populateDescription=true` (current code) | 400 "Invalid format: Must be 'text' or 'html'." |
| same, `format=text` or `format=html` | 400, same message |
| same, multipart field `file` instead of `resume` | 400, same message |
| `format=docx`/`pdf`, `populateDescription=html` | OK. firstName, lastName, email, occupation parsed; 2 work history, 2 education, 11 skills; description 5,028 (docx) / 3,402 (pdf) chars |
| `format=docx`/`pdf`, `populateDescription=text` | OK, same fields; description about 880 chars |
| `format=docx`/`pdf`, no `populateDescription` | OK, same fields; description empty |
| `POST /resume/parseToCandidateViaJson`, `format` in the JSON body only (current code) | 400 "Missing parameter format." |
| same, `?format=text` query param | OK |
| same, `?format=html` query param, HTML body | OK |
| same, `?format=text&populateDescription=text` | OK, description populated (100 chars) |

Conclusions:
1. On `parseToCandidate`, `format` is the input file type (`docx`, `pdf`, ...) and is correct today. The "format" in the error message actually refers to `populateDescription`, which must be `text` or `html`, not `true`.
2. On `parseToCandidateViaJson`, `format` (`text`/`html`) is a required **query** parameter; the body copy is ignored.

## Goals

1. `parse_resume_file` sends `populateDescription=html` (owner choice: keeps CV layout in Bullhorn's Resume tab).
2. `parse_resume_text` sends `format` and `populateDescription` as query parameters, both derived from `content_type`: `text/html` gives `html`, anything else gives `text`.
3. Every CV tool path (`parse_cv`, `parse_cv_text`, `create_candidate_from_cv` in both modes, `attach_cv`) parses successfully against the live tenant.

## Non-goals

- No change to the upload ticket flow (CR41), the tools' signatures, or their responses.
- No change to how the parsed `description` is used downstream. `create_candidate_from_cv` already writes whatever the parser returns in `candidate`, so the Candidate now gets a populated HTML description; that is the intent of the original `populateDescription` flag.
- `query_entities(entity="Candidate")` returning "Query operation not supported for Candidate" (noted in the T40.8 report) is expected Bullhorn behaviour and out of scope.
- No change to `_guess_content_type` (`rtf`/`odt` still go as `application/octet-stream`, per the Sprint 40 note).

## Changes

1. **`client.py`**
   - `parse_resume_file`: `params = {"format": format, "populateDescription": "html"}`. Docstring: `format` is the input file type.
   - `parse_resume_text`: derive `fmt = "html" if content_type.startswith("text/html") else "text"`; send `params={"format": fmt, "populateDescription": fmt}` on the `_request` call. The JSON body keeps `resume` (and `type`); drop the ignored body `format`. `_request` already takes `params`.
2. **Tests** (update the pinned-wrong tests, do not just add new ones):
   - `tests/test_client.py`: the existing `populateDescription=true` assertion becomes an exact query-string check `format=pdf&populateDescription=html` (respx, Sprint 9 payload-assertion pattern). Add a `docx` case.
   - `tests/test_client.py`: `parse_resume_text` with `text/plain` asserts `format=text&populateDescription=text` in the URL; with `text/html` asserts `format=html&populateDescription=html`; both assert the JSON body carries the CV under `resume`.
   - Roughly +3 tests (838 to about 841).
3. **PRD.md**: FR-15, one sentence: "CV parsing shall populate the parsed Candidate description with the CV rendered as HTML." US-31 acceptance, one clause: "and the created Candidate's description holds the CV as HTML."
4. **Docs**: IMPLEMENTATION-PLAN.md sprint row and detail; note in the Sprint 40 section that T40.8 was blocked by this and resumes after CR42.
5. **Skill reference**: add the two parser quirks to `.claude/skills/bullhorn-mcp-api-quirks` (gitignored, agent context only).

## Assumptions (confirm or correct)

- A1: Text mode uses `populateDescription` matching the input (`text` for plain text, `html` for HTML), since there is no HTML layout to keep from pasted plain text. File mode is always `html`.
- A2: Ships as patch Sprint 40B, tagged v0.0.53 after the review loop, like CR39 / Sprint 37B.
- A3: T40.8 live acceptance is re-run after the v0.0.53 deploy, and CR41/Sprint 40 T40.8 is marked done then, not before.
- A4: After the build and before tagging, a live parse-only smoke check (both endpoints, both fixtures) confirms the fix on the tenant, with the same owner permission as the evidence above.
